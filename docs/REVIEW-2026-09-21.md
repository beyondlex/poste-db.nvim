## Bugs fixed

1. **A `connections.toml` created after startup stayed invisible**
   (`connections.lua`, `559d87e`). The "not found" walk-up result was
   cached as `false` with no mtime to re-check and no `invalidate()` hook,
   so the file only appeared after restarting Neovim — which is exactly the
   setup flow the docs describe (write the file, then `USE` it). A miss is
   now re-walked; it costs a few `stat()`s.

2. **`-- @connection <tab>` never learned about connections added
   mid-session** (`completion/data.lua`, `1f01417` + `20ca64e`).
   `ensure_conn_names` cached "I have read this file once", and nothing
   ever invalidated it. The cache is now keyed on the config path +
   `getftime`, and discovery goes through `connections.find_connections_toml`
   so both consumers share one cache and one invalidation rule (this is the
   shape poste-redis already had). `20ca64e` fixes the comment's claim that
   `USE` was the consumer — that verb is poste-redis's syntax. Pinned by a
   new spec file (`sql_completion_cache_spec.lua`).

3. **EXPLAIN refused statements that contain no statement break**
   (`explain.lua`, `148d615`). The single-statement guard was a plain
   `find(";")` on the statement text, so `SELECT 'a;b'`, `'it''s; ok'`, a
   trailing `-- note; end`, and every PL/pgSQL body between `$$ … $$` were
   all rejected with "put the cursor on one statement" — while the cursor
   genuinely was on one statement. The guard now scans for the first
   semicolon outside quotes, comments and dollar-quoted bodies; a real
   break after quoted text is still refused.

4. **…and that scanner was a second implementation of the same rule**
   (`dml_guard.lua` + `explain.lua`, `1e85ce0`). Rather than let the two
   disagree, `dml_guard.strip_non_code` learned dollar quoting
   (`$$…$$`, `$body$…$body$`) — it already masked quotes and comments — and
   EXPLAIN calls it. The 45-line local copy is gone; statement splitting is
   one implementation again, and the `sql_dml_guard_spec.lua` additions pin
   the dollar-quote cases for both consumers.

5. **The translated-SQL footnote wrapped where it was measured, not where
   it landed** (`format.lua`, `dab2a23`). `wrap_line` split with
   `gmatch("%S+")`, which dropped the leading run of spaces the caller's
   layout lived in: the `⚡` row lost its two indent columns while each
   continuation gained the caller's five-cell pad *after* the width check,
   so a long statement rendered mis-aligned and up to seven columns past the
   panel width. A single token wider than the line also pushed the empty
   `current`, emitting a blank row above the marker. The leading run is now
   a hanging indent carried by every row — the width tested is the width in
   the buffer — and the footnote feeds `wrap_line` its own continuation pad,
   swapping the marker onto the first row.

6. **A port that is not a port was concatenated into the URL**
   (`connections.lua`, `d6a39b4`). `port = "{{POSTE_PORT}}"` after a typo'd or
   unset var, `"abc"`, `0` and `70000` each built a syntactically-shaped URL
   that the driver then failed on, far from the config file that caused it.
   Resolution now returns its existing `(nil, err)` contract, naming the
   connection but never the value (`port = "{{POSTE_PASS}}"` is a plausible
   typo). A quoted numeric port stays legal — that is what a dotenv-expanded
   TOML value arrives as — and the Rust store applies the same 1..65535 rule
   to the same file, at resolve time so a `{{VAR}}` port expands first (see
   poste.nvim `REVIEW-2026-09-21.md`).

7. **Pasting a table whose name contains an apostrophe hung the browser**
   (`copy_ddl.lua` + `copy.lua`, `0030041`). The collision probe was
   hand-written `WHERE table_name = '%s'`, so `o'brien` closed the literal
   early and the query errored — and the probe's error handler fails *closed*
   (`cb(true)`, "pretend it exists rather than clobber it"). Every candidate
   name therefore reported "taken", and the auto-suffix loop that follows
   (`_copy`, `_copy2`, …) asked for the next one forever: an unbounded stream
   of failing queries with no UI feedback. The name and schema now go through
   `ident.quote_literal` at build time, and the bump loop is capped at
   `MAX_NAME_BUMPS = 100` candidates; past the cap it hands back the last
   name so `CREATE` fails loudly instead of hanging. The cap is not the fix
   for the bug — it is the end of the class "fail-closed probe + unbounded
   search", which will recur with any other probe error (revoked
   `information_schema`, a connection that died mid-paste).

8. **Rename acted on the wrong schema** (`ops_sql.lua`, `0147c7e`).
   `rename_table_sql` and `rename_column_sql` emitted a bare table name while
   every sibling generator went through `qualified_table_ref`, so renaming a
   table or column browsed under a non-`public` Postgres schema hit whatever
   the session `search_path` resolved to — usually a different relation, or
   an error that looked like the browser disliking the name. The two
   operations now qualify the target like `SELECT *` and `ADD COLUMN` do.
   `operations.new_column`'s prompt flow had the same bare-name bug, plus an
   `if dialect == "mysql"` branch that re-assembled the identical string.

9. **`mt` / `ma` on SQLite did nothing** (`table_ops.lua`, `0147c7e`). The
   SQLite DDL generators answer with a comment *block* (one Lua string
   containing `\n`), and `nvim_buf_set_lines` rejects any replacement item
   that contains a newline — so the call errored, the buffer stayed
   untouched, and the mapping looked dead with no visible cause. `insert_ddl`
   now `vim.split`s the generated text before inserting.

10. **`table_ops` quoted identifiers with its own private rule**
    (`table_ops.lua`, `0147c7e`). A two-branch local helper (backticks for
    mysql/mariadb, double quotes otherwise) predated clickhouse and mssql: a
    clickhouse name came out `"x"`, which that engine does not accept. It is
    now `ident.quote`, and the module's `sp_rename` call gained the same
    apostrophe doubling `ops_sql` already had. ADD COLUMN from
    `operations.lua` and from `table_ops.lua` now both delegate to
    `ops_sql.add_column_sql` — the two DDL generators in this repo can no
    longer disagree, which is the same drift class this family keeps hitting
    across repos.

11. **A junction table's INSERT template was unparseable**
    (`operations.lua`, `a77c878`). The template deliberately skips primary
    keys, but a join table is *all* primary keys, so it produced
    `INSERT INTO "t" () VALUES ()`. It now falls back to the key columns,
    matching what `update_template` already did for its SET list.

12. **Dead dispatch conditions in the browser operations**
    (`operations.lua`, `0147c7e`). `select_star` and `show_ddl` tested
    `node_type == "view"`; the tree has no such node type (a view is a
    `table` node with `meta.table_type == "VIEW"`), so the tests could never
    fire. Worse, `select_star`'s column branch looked up
    `context.line_to_node[node] and 0 or 0` — indexing a node table by a node
    *table*, i.e. always `0` — which made the whole branch a no-op and
    silently relied on the fallback below it. Both paths now resolve through
    the cursor line and are pinned by specs. This one is a cleanup, not a
    behaviour change: its specs fail nothing when reverted, which is exactly
    what "pinned intent" means here.

13. **Pasting a routine whose body mentions the other routine kind pasted
    nothing** (`copy_ddl.lua`, `039b95a`). The rename helper located the
    statement with `upper:find("PROCEDURE") or upper:find("FUNCTION")`, which
    answers with the PROCEDURE hit whenever that word appears *anywhere* —
    including in a `CREATE FUNCTION` body, i.e. after the name being rewritten.
    The scan then started too late, matched nothing, and returned the
    definition unchanged; the paste ran the source definition verbatim. On
    Postgres that is `pg_get_functiondef` output, which begins `CREATE OR
    REPLACE FUNCTION`, so the operation reported success while creating no
    copy and rewriting the original in place. The keyword is now the earliest
    of the two.

14. **`r` in the SQL log now does what its documentation says**
    (`log_viewer.lua`, `09db057`, experience fix rather than a bug). It yanked
    the entry's SQL into `"` and `+` and notified the user to paste it
    somewhere — i.e. it was `y` with extra words, while the docs promised a
    re-run. Executing from the float was rejected on purpose: no DML guard, no
    confirmation, no dataset window, and a logged `DELETE` is as destructive
    the second time. `r` now closes the float and writes the statement into a
    fresh `sql` buffer, where the FileType autocommand installs the guarded run
    keymap, prefixed with `-- @connection <name>` when the entry recorded a
    name (a redacted URL is dropped — it resolves to nothing). The winbar hint
    gained `y=copy  r=to buffer`, the two keys it never listed.

15. **Paste collision checks asked about the wrong schema** (`copy.lua`,
    `47c361a`). Item 7 made `dialect_table_exists_sql` take a schema and render
    it through `quote_literal`, and `resolve_conflict_names` dutifully threaded
    `items[i].schema` into its probe — but the default probe called
    `check_table_exists` with six arguments, so the function's seventh (`schema`,
    already in its signature) stayed `nil` and every Postgres check ran against
    `public`. Since the recreated table keeps its source schema qualifier, the
    check and the write disagreed: a taken `app.users` read as free (the paste
    then failed at CREATE) while a taken `public.users` renamed a perfectly free
    `app.users` to `users_copy`. MySQL is unaffected and deliberately so — its
    `SHOW CREATE TABLE` output carries no database qualifier, so the object
    really does land in the connection's current database, which is what the
    probe asks.

## Round 5 — one directive rule, and the harness that hid the completion specs

The Rust side of this round is `poste.nvim/docs/REVIEW-2026-09-21.md` Rounds
4–6; the items below are this repo's half of those stories, plus the two that
only live here.

16. **A directive inside a string literal suppressed the AI header**
    (`ai/actions.lua`, `da632fa`). `append_header` asked whether the block
    "already carries a directive" with an unanchored `text:match`, so
    `SELECT '-- @connection other' AS note` — or that text in a prose comment —
    was enough to skip the header, and the block then ran against whatever
    connection the buffer had instead of the chat scope's bound one. The check
    now walks the block's lines through `constants.match_directive`, the
    anchored rule `file_exec.lua`, the completion handlers and the Rust CLI
    already used; the new spec keeps the opposite case honest (a directive-like
    string still gets its header).

17. **`file_exec.lua` held the fourth copy of that pattern** (`f5357c1`).
    Four hand-written versions of one anchored rule (constants, the completion
    handlers, the CLI's reader and stripper, and here) is how 16 stayed
    invisible: the fix belongs to the rule, not to a file. It calls
    `constants.match_directive` now, and `extract_connection_directive` is
    reachable from the specs through `M._test`, which assert the same shapes the
    Rust test rejects — the drift needs a violation in two repos to happen
    silently again.

18. **The completion prefix was derived twice, and the Lua copy could not see
    quotes** (`completion/handlers.lua`, `d8e30ce`). `handle_dot_column` matched
    `line_before` against `[%w_]+%.([%w_]*)$` to filter columns — a second,
    narrower version of the rule Rust already answered. For `SELECT "p"."ti` it
    matched nothing, filtered on an empty string and listed every column of the
    table. It uses `rust_ctx.prefix` now, with the Lua pattern kept only as the
    fallback for when no Rust context exists; the paired Rust fix is item 20 in
    that file (an unterminated quoted name used to lose its last character, so
    this side would have filtered on `"`).

19. **`$POSTE_BINARY` never reached the process that needed it** (`state.lua`,
    `6227caf`). plenary runs each spec file in a child nvim started without
    `-u`, so the override set in `tests/minimal_init.lua` applied only to the
    parent. Inside the child no binary was found and every Rust-dependent
    assertion failed on an empty completion list — 14 red in
    `sql_completion_spec` alone — or printed SKIP while the file reported
    success, which is the version that survives a CI grep. An environment
    variable is the one channel the child inherits, so the resolver now reads
    `vim.g` → `$POSTE_BINARY` → `$PATH` and the bootstrap exports what it
    picked; a CI checkout with a non-standard layout gets the same hook.

20. **The env.json reader could abort resolution and could not read a flat
    file** (`connections.lua`, `d4f8356`, `4f4a77b`). The selected section was
    copied verbatim into the substitution table, so one nested object
    (`"LABELS": {"team": "db"}`) reached `substitute_vars` and `gsub` answered
    `invalid replacement value (a table)`; a number stayed a number where the
    CLI reads text; a file without the requested stanza yielded no variables
    even though `poste connection list` resolves it as a flat map; and the
    reference pattern accepted only `[%w_.]` names, so `{{DB-HOST}}` expanded
    for the CLI and reached the driver as literal braces from here. It now
    mirrors the CLI's `scalar_vars` rule and `\{\{([^}]+)\}\}` name charset.

## Round 6 — the installer was still carrying its own copy of the binary rule

Items 19 and 20 narrowed this repo's copies of the CLI's rules down to one
each; the last one was not in a resolver but in the startup check, and it is
the reason the README could keep being wrong twice.

21. **`install.ensure()` had drifted from the lookup it duplicated**
    (`install.lua`, `1494696`). Setup called `install.ensure()` once per
    session, and that function walked its own 47-line candidate list:
    `vim.g.poste_binary`, `state.config.poste_binary`, the plugin-relative dev
    builds, the CWD dev builds, the install path. Every step tested
    `filereadable` only, and `$POSTE_BINARY` and `$PATH` were absent. Two
    consequences, both user-visible: a `g:poste_binary` pointing at a file
    without the exec bit was returned as *the answer*, so the caller never
    reached the download that would have replaced it; and the documented "put
    `target/release/poste` on your PATH" install was invisible to the startup
    check, which downloaded a release into `stdpath("data")` — and that copy
    then outranks `$PATH` in the resolver, so the user's own build silently
    stopped being used. `ensure()` now asks `state.find_poste_binary()` and
    only downloads when that returns nil: one rule, one copy, and the two
    things a lookup cannot do (download, notify) are what stays here.
    `tests/sql/sql_install_spec.lua` covers it; against the previous `ensure()`
    2 of its 4 cases fail — `refuses a readable but not executable override`
    and `uses a binary on $PATH instead of downloading a release` — and the
    other two pin the shape of the delegation (returns the resolver's answer
    with no download; downloads exactly once when nothing is usable).

22. **The README described an install path the code did not implement**
    (`6016a37`). Both the README and `doc/poste-db.txt` said the binary is
    "downloaded on first setup", which had only ever been the last resort.
    They now state the five-step order, the readable-*and*-executable rule, and
    `$POSTE_BINARY` as the channel for headless and CI processes — the same
    contract `state.lua` documents in its docstring.

## Round 7 — diagnostics: the lookup now says who won

Round 6 removed the last duplicate of the binary rule; what was left was that
the rule itself was unobservable. Five steps of priority ordering, and no
command printed any of them.

23. **`find_poste_binary()` returned a path but not its provenance**
    (`state.lua`, `0a2ec36`). The answer to "I built `target/release/poste` and
    the plugin is running something else" existed only inside the function. It
    now returns `(path, source)` with one label per candidate
    (`g:poste_binary`, `$POSTE_BINARY`, `installed release`, `dev build in cwd`,
    `dev build beside plugin`, `$PATH`), and both diagnostic surfaces print it:
    `:PosteDbInfo` gets a `from:` line next to the path and build time,
    checkhealth gets `poste binary: <path> (from <source>)`. The pair is
    returned rather than a path with an embedded label so the transport-facing
    callers keep getting exactly what they spawn.
    Also in this item: the not-found error now names `$POSTE_BINARY`, which was
    the only channel documented for headless and CI processes.
    `tests/sql/sql_state_spec.lua` gained a `binary resolution source` describe
    (5 cases: each label, and nil + nil when nothing is usable).

24. **A dead helper kept a shell-interpolated command alive as documentation**
    (`nav/detect.lua`, `002c71a`). `build_context_detect_command(bin, offset,
    dialect)` returned a single command string with `--dialect <value>`
    concatenated in unquoted, and its only test asserted that shape. Nothing
    called it: go-to-definition spawns an argv table through `vim.system`
    (`nav/handlers.lua:85`), which needs no quoting because there is no shell.
    Deleted, test included — leaving it meant the next caller would have had a
    worked example of the wrong way to invoke the CLI.

25. **The Windows install steps passed their paths to PowerShell unquoted**
    (`install.lua`, `b118bb3`). `vim.fn.system` in list form means no
    *shell*, but
    `powershell -Command` then joins its remaining arguments and parses them as
    a PowerShell *command line*, so `Expand-Archive -Force -Path <BIN_DIR>`
    with the archive directory arriving as a separate argv element was still
    split at the first space. `stdpath("data")` is
    `%LOCALAPPDATA%\nvim-data\…`, i.e. under `C:\Users\Jane Smith\` for any user
    whose name contains a space, and the zip branch of the download would fail
    there (and re-parse `$var` and `;` in the same position). Both `-Command`
    sites now build one command line with `M.ps_literal(path)`, which uses
    PowerShell's single-quoted literal and doubles embedded `'`. Not exercisable
    on this machine — the three `ps_literal` specs pin the quoting rule, and the
    call sites are one-look greppable; the pre-existing extraction check after
    them is what would have caught the failure at runtime.

26. **Four files required the same module under two names** (`f64c980`).
    `local state` and `local sql_state` sat adjacent in `buffer/init.lua`,
    `buffer/nav.lua`, `completion/data.lua` and `db_browser/async.lua`, so any
    question about what reads `state.last_response` (or the binary, or the log
    call) had two answers and only one of them was checked per file — the
    usages were not even split along any real boundary, they were a merge
    leftover. Each file kept the alias its own majority used. Grep-based, with
    the distinction recorded: a `local x = require(...)` *inside* a function
    (`session.lua:45`, `edit_commit/init.lua:236`) is a deferred require, which
    is this repo's style in command callbacks, not a duplicate alias.

## Round 8 — the one platform the contract did not cover

27. **The lookup could not see the file the installer writes** (`state.lua`,
    `2969a41`). Rounds 6 and 7 left `find_poste_binary()` as the single owner of
    the binary rule; this is the bug that survived them. Every candidate it
    offers is spelled without an extension — `stdpath("data")/poste/bin/poste`,
    `target/{debug,release}/poste`, `bin/poste` — while `install.lua`'s
    `binary_path()` appends `.exe` on Windows, which is also where cargo puts
    it. On that platform `ensure()` therefore downloaded a release the next
    lookup could not find, i.e. re-downloaded at every startup, and
    `:checkhealth poste-db` / `:PosteDbInfo` reported no binary unless
    `vim.g.poste_binary` named the `.exe` in full — while the download
    failure's own hint tells the user to set an extension-less
    `"/path/to/poste"`. No machine in the
    development path runs Windows, so seven rounds of reading this file did not
    cross-check the two spellings against each other.
    `usable(p)` becomes `resolve_candidate(p)`, returning the path that runs:
    `p`, or `p .. ".exe"` when the new `state.is_windows` (derived from
    `os_uname().sysname`, the same test `detect_platform()` uses) and only that
    exists. An exact candidate still beats the guess, order and labels are
    unchanged, and a configured path now works with or without the extension.
    poste-redis's copy carries the identical fix (`90d5af8`).
    4 specs in `binary resolution on Windows`; reverting only the production
    change leaves exactly the 2 that pin the bug red (`finds the .exe the
    installer wrote`, `adds the .exe to a g:poste_binary spelled without one`).
    The other 2 — the exact match winning, and no `.exe` matching off Windows —
    guard against the fix overshooting, so they pass before it as well.

## Round 9 — the startup download end to end, and the test that read the whole machine

28. **Both release downloads had no time ceiling** (`install.lua`, `c804b25`).
    `ensure()` runs from `setup()`, so `verify_checksum()`'s checksum fetch and
    `download()`'s archive fetch are on the editor's startup path, and each one
    was a bare `curl -fL url -o path`. curl's own defaults are a 300-second
    *connect* phase and no transfer limit at all: a captive portal or a
    firewall that answers the SYN and drops the rest freezes Neovim until the
    OS socket timeout expires. To the user that is a hung plugin load, not a
    failed download, and it happens before any of this plugin's UI exists to
    report it. `M.curl_argv(flags, url, out, max_time)` now emits
    `--connect-timeout 10` plus a per-fetch `--max-time` (20s checksum, 180s
    archive) and keeps argv in list form — the shape Round 7 established as the
    reason no path can reach a shell. The same audit checked the asset names
    and layout against `poste.nvim/.github/workflows/release.yml`: the
    `-fL`/`-sfL` flags, the `sha256sum` lowercase digests, the flat archive
    members and the five matrix names all match, so no change was due there.
    `verify_checksum()` also leaked `checksum.tmp` when `io.open` failed after
    a successful fetch; that branch now removes the file like the one above it.
    poste-redis carries the identical change (`3e983aa`).
    4 specs in `install curl_argv`, and `curl_argv` is a pure function of its
    arguments specifically so they can assert on argv without a network.

29. **`export run` asserted against the system pasteboard**
    (`tests/sql/sql_export_spec.lua`, `ba8999c`) — the suite's one
    machine-shared dependency, and the reason the gate went red once and stayed
    green afterwards. `copies to the clipboard for destination=clipboard`
    reported 34/0 standalone and 33/1 inside the 95-file run. It was not the
    new `curl_argv` work: both `setreg("+")` and `getreg("+")` shell out to
    pbcopy/pbpaste, and every other spec process in the run is doing exactly
    the same thing. Measured directly — twelve headless instances each writing
    a unique value and reading it straight back — 11 of 12 read someone else's
    value. So the case was never testing this plugin; it was sampling whatever
    the pasteboard held at that instant, and the failure message
    (`Expected to be truthy, but value was: (nil)`) was `find()` missing on a
    path written by an earlier test in the same file. The fix is a
    `g:clipboard` provider that stores into a table: `provider#clipboard`
    consults `g:clipboard` on every access (unlike the once-loaded builtin, so
    no reset dance is needed), which keeps the assertion on the text the
    exporter actually handed to the clipboard. Two uncovered behaviours came
    with it: a file export puts the absolute *path* on `+`, never the payload,
    and both destinations also fill the unnamed register so a paste still works
    where no clipboard tool exists. poste-redis's `yank_spec` reaches the same
    registers by stubbing `vim.fn.setreg`; the provider is the better idiom of
    the two because it keeps the real `setreg` in the loop, and it is recorded
    here rather than ported because the redis specs pass either way.

30. **The checksum compare rejected a good download** (`install.lua`,
    `db5527a`). Found by reading the three hasher branches against the release
    asset rather than against each other: `verify_checksum()` ended with
    `actual == expected`, where `expected` is the digest from
    `poste-<platform>.tar.gz.sha256` — `sha256sum` output, lowercase — while on
    Windows the fallback hasher is `certutil -hashfile`, which prints the same
    digest uppercase. So the compare is false for every byte-correct archive on
    the one class of machine that reaches that branch, since it is chosen
    precisely because `sha256sum` and `shasum` are absent. The user-visible
    result is the plugin reporting `Checksum mismatch — download corrupted`,
    deleting the archive that is not corrupted, and starting over at every
    startup: the retry loop item 27 described, reached by a different line.
    `M.checksum_matches(actual, expected)` lowers both sides — a hex digest's
    case carries no information, so the strict compare was only ever comparing
    two tools' formatting habits.
    5 specs; reverting just the compare leaves exactly the uppercase case red,
    and the other 4 (lowercase pair accepted, one-nibble tamper rejected in both
    directions, same-length-different-digest rejected, truncated digest
    rejected) stay red for any compare loose enough to satisfy length or
    prefix alone — the overshoot guard matters more here than elsewhere,
    because "make the mismatch go away" is exactly the tempting wrong fix.
    poste-redis carries the same change (`5479f62`), and `release.yml` in
    poste.nvim now records the asset name / flat archive / digest-format
    contract this repo's installer depends on, with README pointing at it.

## Round 10 — semantic diagnostics: four defects, each pinned by its own spec

`semantic_diagnostics.lua` had been through the earlier passes only as a whole
file (the `is_catalog_ref` and `WITHIN GROUP` work). Reading the *lifetimes*
instead — who sets the in-flight flag, which schema a name is checked against,
what a cache key means — produced four defects. All four are in the
"silently stops being useful" family rather than the "crashes" family, which is
why they survived: the module reports nothing when it gives up, so a giving-up
module is indistinguishable from a correct one.

31. **A single failed schema fetch muted a buffer for the rest of the session**
    (`semantic_diagnostics.lua`, `cc69b5e`). `M.update` set
    `_pending_checks[buf] = true` before `fetch_tables` and cleared it inside
    the callback — but two measured `jobstart()` behaviours meant the callback
    never ran. `jobstart` *throws* `E475` when `argv[0]` is missing or not
    executable (it returns nothing, so no `on_stdout`/`on_exit` either), and
    `argv[0]` here comes from `find_poste_binary()`, which caches a path a
    reinstall or a stale `g:poste_binary` can invalidate under us; and with
    `stdout_buffered = true` a job that writes nothing to stdout still fires
    `on_stdout` with a single empty line, which the old guard returned on
    without calling back. Either way the flag stayed set, and since
    `_pending_checks[buf]` gates the only fetch path, that buffer never
    re-checked its schema again — including after the binary came back.
    `run_introspect(args, store, callback)` now holds both fetches, wraps the
    spawn in `pcall`, treats a non-positive return as failure, and funnels
    every outcome through `settle()`, which fires the callback exactly once.
    4 specs in `semantic_diagnostics fetch failure recovery`: a rejected path,
    an exit-0-silent binary, and two controls (non-JSON output, exit 7) that
    were already green — they are there to show the recovery is the general
    property, not the two patches.

32. **A cross-database reference was checked against the wrong database**
    (`semantic_diagnostics.lua`, `319e5a9`). With the cursor on connection
    `connA` / database `blog`, `SELECT full_name FROM otherdb.users` was
    validated against *blog*'s `users`, because the qualified table produced a
    diagnostic only when `otherdb` happened to be in the cache and otherwise
    fell through to the current schema. Wrong in both directions at once: a
    real column was flagged missing, and a typo that named some `blog.users`
    column was accepted — with a message naming the database it had never
    read. Now `schema_for(conn, db)` (memoised per statement) returns nil for a
    database with no cached table list, and nil means *skip*: "not cached" is
    "cannot tell", never "wrong". Which database each name belongs to is
    recorded per statement in `ref_db`, so the columns of a qualified table are
    checked against the same list as the table itself; a name used by two
    different databases in one statement is stored as `false` and checked
    against neither, because guessing is what caused this item. 4 specs.
    Recorded as accepted behaviour: a postgres *schema* prefix (`FROM
    public.users`) is also treated as a database, misses, and is therefore not
    checked — the cache has no schema dimension (see item 34 for the same
    reading applied to three-part names).

33. **Table names were compared case-sensitively against a folded cache**
    (`semantic_diagnostics.lua`, `83430e8`). Unquoted identifiers fold to
    lowercase in postgres and are case-insensitive in MySQL and SQLite, but
    `build_schema` keyed its column lookup by the table name *as the fetch
    wrote it* while the lookup used `tbl:lower()`. So `SELECT * FROM USERS`
    flagged every column of a table cached under `users` — and `fetch_columns`
    stored under the name as typed, so `introspect --table USERS` (which
    postgres answers with zero rows) filed an empty list under `USERS`.
    `build_schema` now folds and *unions* the cached keys, and `fetch_columns`
    stores folded. The same commit gives an empty cached column list its real
    meaning: `columns = { users = {} }` came from a failed or empty fetch, and
    reading it as "this table has no columns" flags every reference to it, so
    `column_problem` treats it as "not known yet" and schedules a re-fetch.
    4 specs; reverting only the `next(cols)` guard leaves exactly one red,
    which is why the guard is called out separately.

34. **`database.schema.table` was read as one table name**
    (`semantic_diagnostics.lua`, `566bb3e`). `object_reference` is
    `identifier ("." identifier)*`, so two-part and three-part refs arrive with
    three and five children. Only the three-child shape (and the
    single-identifier one) was destructured; everything longer was taken whole,
    which turned the legal postgres/ClickHouse `FROM blog.public.users` into a
    table literally named `blog.public.users` — reported missing from whichever
    database the statement ran against, in every file that spells its
    references out. `dotted_reference()` now reads the shape once: trailing
    identifier = table, leftmost = database (true for postgres, MySQL and
    ClickHouse alike), components in between = schemas, which the
    per-database cache cannot express and therefore leaves unchecked. The same
    whole-text mistake was live in two more spots: `SELECT blog.users.bogus`
    qualified a table named `blog.users` (matches nothing, so every typo in a
    fully qualified column passed), and a table whose database is *not* cached
    was left out of `ref_db` entirely, so its unqualified columns fell back to
    the current database — item 32's bug reached by another path. `add_table`,
    `add_column`, `relation`'s alias and the INSERT branch now share one
    `unquote()` instead of repeating the same `gsub` pair six times. 5 specs,
    with `public` and `blog` deliberately holding different `users` lists so a
    wrong choice of which component is the database cannot pass all of them.

    Gate for the round: **1491 Success / 0 Failed / 0 Errors** (95 spec files),
    up from 1474 by exactly these 17 specs; `luacheck .` clean over 235 files.
    Two harness facts learned the hard way, both of which hide red tests rather
    than causing them: `tests/run_one.sh` redirects `XDG_DATA_HOME` to a temp
    dir with no tree-sitter SQL grammar installed, so a targeted run silently
    `pending`s every parser-dependent spec — run the parser cases with
    `XDG_DATA_HOME="$HOME/.local/share"` (the env vars are `:-`-defaulted, so
    an outer value wins) and guard the file with `ts_stmt.check_parser()`;
    and `vim.treesitter.language.get_lang("sql")` returns "sql" even when no
    parser can be built, so it is not usable as that guard. Neovim also does
    not recycle buffer numbers within a session, which rules out the
    "delete a buffer and watch the next one inherit its stale diagnostic
    namespace" class of bug the harness might otherwise have simulated.

## Round 11 — the import path: what a bad chunk size does, and what the preview promises

The import flow (`import.lua`, `import/format.lua`, `import/mapping.lua`,
`import/preview.lua`, `import/execute.lua`) had only ever been read for the
parser and the type coercion. Reading it as a *pipeline with a config input and
a UI output* turned up four things, three of them in the two ends that no spec
covered: `execute_import`'s chunk loop and `show_preview`'s renderer.

35. **An `import_chunk_size` below 1 loops forever, and a non-numeric one
    throws mid-import** (`import/execute.lua`, `b0bce25`). The loop advances by
    `end_idx + 1`, where `end_idx = min(start + chunk_size - 1, #rows)`. With
    `chunk_size = 0`, `end_idx` is `start - 1`, so no statement is generated,
    the response comes back with nothing in it, and `send_chunk(start)` is
    called again — the same empty chunk, forever, with the "Imported N rows"
    notice never arriving. `chunk_size = -3` is identical, and a string like
    `"wide"` survives `start + "wide" - 1` only until the arithmetic throws,
    *after* the first chunks have already been written to the database. Both
    values are ordinary user config (`doc/poste-db.txt` lists the option, and
    `config.lua` has no validator for it), so read the value as a number,
    floor it, and clamp to 1.
    6 specs in `sql_import_execute_spec.lua`, which stubs `exec_run.run_async`
    with a synchronous `on_response` and asserts the chunk boundaries (2+2+1
    over five rows), the clamped cases, and that a per-statement error in the
    second chunk is attributed to absolute row 3 with `chunk_start 3 /
    chunk_end 4`. The stub aborts the loop past 30 chunks — that is what makes
    the infinite case show up as a failing test instead of a hung suite.
    Reverting only the clamp leaves exactly those three red.

36. **"Import blocked" printed the rejected columns as the matched ones**
    (`import.lua`, `9c09dc4`). When the file has a column the table lacks, the
    import aborts and names those columns — then appended
    `(matched: <every column in the file>)`, because it printed
    `parsed.columns` instead of `col_map`. Since "matched ∪ unmatched = the
    file header", the parenthetical was the same list twice with the opposite
    label, which is the sentence that tells a user whether to rename the file
    or the table. Now built from `col_map[*].import_name`.

37. **Two mapping helpers took arguments they never read**
    (`import/mapping.lua`, `f68cf8f`). `build_row_values` pre-filled `row[i] =
    nil` for every table column — a no-op in a Lua table — which is what the
    unused `num_table_cols` existed for; `validate_and_type` took `table_cols`
    and `unmatched_table` purely for their eventual absence. Both are now
    `col_map`-only, and the comment says the part a reader cannot infer: the
    row is *deliberately sparse*, because `dml.generate_insert` reads an absent
    value as "omit the column, let the default or sequence apply" and an
    explicit NULL as NULL. Same shape, different meaning, and the difference is
    carried by `coerce_value` returning Lua `nil` for an empty cell and
    `vim.NIL` for the literal `NULL`. Behaviour and all 46 import specs
    unchanged.

38. **A clean preview opened with a red zero** (`import/preview.lua`,
    `f189eac`). The summary line's third number — "N with errors" — was
    highlighted `DiagnosticError` unconditionally, so a file with nothing wrong
    with it showed `0` in error red. The same three searches fed each other's
    end offsets without checking that the previous one matched, so a line that
    ever stops starting with `Parsed: <num>` turns the preview into an error
    instead of a missing highlight. The group list is now built conditionally
    and walked once. While pinning this, `math.max(4, 0)` / `math.max(5, 0)` —
    the mapping table's minimum column widths, with the second operand a
    leftover that always lost — became plain initialisers.
    `sql_import_preview_spec.lua` (8 specs) is the module's first test: the
    dialog stub captures the rendered lines and highlights, which lets the
    layout (mapping table, `NULL` for an empty cell, `... (1 more row(s))`,
    `(missing: … <- DEFAULT)`) and the *absence* of a red zero all be asserted
    without a UI. Removing only the `#bad_rows > 0` guard turns exactly one
    spec red.

    Gate for the round: **1505 Success / 0 Failed / 0 Errors** (97 spec files),
    up from 1491 by these 14 specs; `luacheck` clean. One Lua trap worth
    recording, hit while writing item 38: `local s, e = ok and text:find(...)`
    gives `e` as *nil* even when `ok` is true, because an operator in an
    assignment list truncates the call to one value — the guard I added to make
    the highlight loop safer than the original was itself the crash.

## Round 12 — what a cell means is the column's business

Round 11 read the import pipeline's *ends*; this one read its *middle*, by
driving a parsed cell all the way to the SQL text and asking whether the row
ends up holding what the file said. Two answers were no, and both were the same
mistake seen from two sides: the value's own spelling decided its type, and the
column it was heading for was never consulted.

39. **`true` in a text column became an unquoted `TRUE`** (`import/mapping.lua`,
    `4df1d24`). `coerce_value` matched the word case-insensitively and returned a
    Lua boolean for *any* column, and `dml` renders a Lua boolean as bare
    `TRUE`/`FALSE` — so importing a CSV whose `note` column said `true` gave
    postgres `column "note" is of type text but expression is of type boolean`,
    and MySQL the value `1`. The word is data unless the column can hold a
    boolean, which includes MySQL's spellings (`tinyint(1)`, `bit`, `bit(1)`)
    and, as before, a column introspection gave no type for. `1`/`0` → `true`/
    `false` stayed restricted to genuine boolean columns, where it is the only
    spelling some dumps use.
    The same round consolidated the *second* half of that question — does this
    column hold numbers? — into `lua/poste-db/types.lua`. `import/mapping.lua`
    and `format.lua` each kept their own type table with different keys, and
    neither matched the names introspection actually returns: `numeric(10,2)`,
    `double precision`, `INT4`. The shared lookup matches on the root word of the
    lowercased name, which covers the whole family at once (`int4`, `int8`,
    `int32`, `UInt64` all land on `int`), and `smallserial` — present in the
    editor's and format's tables, missing from the mapper's — came along with it.

40. **Digits aimed at a text column went out as an integer literal**
    (`dml.lua`, `5ba9903`). `quote_val` decided "is this string a number?" from
    the string alone, so a cell holding `42` was emitted bare even in a `varchar`
    column. That is not cosmetic: postgres rejects `INSERT … VALUES (42)` into a
    text column, and `DELETE FROM t WHERE code = 42` is
    `operator does not exist: text = integer` — the row the user clicked cannot
    be addressed at all. MySQL and sqlite apply the column's affinity and store
    `'42'`, so the same statement passes there, which is why the defect survived:
    it only ever failed on the dialect whose literals are typed. The generator now
    takes the column's type from whichever shape the caller holds (`ctype` on
    dataset layout columns, `type` on import's normalized ones, `col_type` on
    browser nodes) and quotes digits that are not headed for a numeric column.
    No type means the old permissive answer, so the 17 pre-existing `dml` specs —
    which build columns out of names alone — are a compatibility case rather
    than collateral.

41. **The two halves had never been tested together** (specs, all three
    commits). Every prior spec pinned one module's behavior in isolation, which
    is exactly how 39 survived: the mapper's "coerces booleans" spec asserted a
    Lua `true` for a `varchar` column, and `dml`'s spec asserted bare literals
    for columns with no type at all. Both were true and the pair was wrong.
    `sql_types_spec` (6, new) and four new `import mapping` cases cover the
    mapper's side, five `dml` cases the generator's, and three of the mapping
    cases — `the file to the INSERT, end to end` — run
    `validate_and_type → normalize_columns → generate_insert` the way
    `execute_import` does, so a change on either side has to break something.
    The rewritten mapper specs record the new rule *and* the reason
    (`'true'` in text, `TRUE` in `tinyint(1)`).

42. **The renderer's third copy of the type list** (`format.lua`, `ed6f680`).
    Right-alignment consulted `NUMERIC_CTYPES`, keyed on the *normalized* ctype,
    so any declaration `normalize_type` does not rewrite — which includes every
    size-tagged one, since the map has no key for `decimal(10,2)` — fell through
    to left-aligned text. Same lookup the mapper now uses, one fewer list to
    keep in sync; `sql_format_bigint_spec` gained the `decimal(10,2)`/`UInt64`
    case and pins that a varchar full of digit strings stays left-aligned.

    Gate for the round: **1521 Success / 0 Failed / 0 Errors** (98 spec files),
    up from 1505 by these 16; `luacheck` clean (238 files).

## Round 13 — what the browser and the dataset promise the screen

Rounds 11–12 read the paths that *produce* SQL. This one read what the UI
asserts about it afterwards: the page counter, the search highlight, the tree
search's "jump to match", the DDL form's geometry, its list entries and its
close-on-leave, the browser's cursor → node resolution, and where a paste
lands. Each of these is a small claim about the screen — "match 3 of 7",
"this row is the focused field", "page 2 of 5" — and seven of the nine were
computed from a stale or second-hand model of the state they described. The
eighth (45) was a type the JSON decoder hands back; the ninth (50) a marker
drawn from a flag nothing ever read.

43. **The page count was only ever written on the paginated branch**
    (`dataset.lua`, `apply_page_bounds`, `a8b3a3c`). `num_pages` and the clamp on
    `page` lived inside `refresh_page`'s `if paginated`, so a filter or sort that
    shrank the row set left the old count standing: the winbar advertised
    `P:7/20` above ten visible rows, `H`/`L` climbed that phantom page count
    without the buffer changing, and the search counter divided by it. The
    recompute moved into `Dataset.apply_page_bounds(tab, total_rows)`, called
    from both render paths (`buffer/page.lua` and `buffer/init.lua`), and the
    branch condition now reads the `pages` value it returned instead of
    re-deriving `total > page_size` a second way. `sql_page_bounds_spec` (8)
    pins the arithmetic and, through a stubbed `format`/`buffer`, that
    `refresh_page` on a filtered single-page view repairs `num_pages` *and*
    pulls an out-of-range `page` back.

44. **Search highlights were sliced by page while every row was on screen**
    (`buffer/search.lua`, `eeb4cae`). The matcher builds a flat list plus
    per-page buckets; the highlighter read only the buckets, so with pagination
    switched off (`toggle_pagination`, or a result set under one page) matches
    on other pages got no highlight at all — the count said "5 matches" and the
    buffer showed one. Now `is_paginated(tab)` (a new helper, replacing three
    copies of the same conjunction) picks the flat list when the view is not
    paged, and the `vis_row` re-base that the buckets imply is skipped with it.
    `sql_search_highlights_spec` gained a 2-case `page slicing` block that
    renders a three-row buffer and asserts which rows carry a mark, unpaged and
    paged.
    The same commit changed the substring slice from `line:sub(ext_start, …)` to
    `line:sub(ext_start + 1, …)`; a headless probe showed the old pair of
    off-by-ones cancelled exactly, so that half is a clarity change, not a fix,
    and the spec says so instead of claiming a bug.

45. **A `null` in column metadata crashed the tree** (`db_browser/tree.lua`,
    `c0676ab`). Introspection JSON decodes `null` to `vim.NIL`, which is
    *truthy* userdata, so `item.type or "?"` kept the null and handed it to the
    next string operation. Two of those run while the tree is being drawn —
    `flatten_tree`'s `" " .. meta.col_type` and `meta.extra:lower()` — so one
    column whose type or extra came back null made the whole tree fail to
    render; `show_column_info`'s `"'" .. meta.comment` threw on any column
    without a comment, and its `tostring` turned an absent default into the
    word `nil`. `tree.null_or(value, fallback)` collapses a null at the node
    boundary, in both builders that feed concatenated fields (`table_type` and
    `comment` on tables, `col_type`/`extra`/`comment` on columns); `default`
    and `collation` stay raw because their readers test for `vim.NIL`
    explicitly, which is the only place that test is meaningful — a NULL
    default and no default at all are different facts.
    `sql_browser_column_meta_spec` (7) covers both builders and the float's
    rendered rows.

46. **Tree search navigation jumped to the wrong window and skipped a
    match** (`db_browser/actions.lua`, `de76765`). `search_prev` passed
    `search_state.current - 1` into `do_jump`, which normalizes with
    `((index - 1) % n) + 1`; from `current = 0` — the state right after a
    search, before any jump — that is `n - 1`, so `N` immediately after `/`
    went to the second-to-last match and never showed the last one.
    `search_prev` now names that state (`current == 0` means "searched, not
    jumped yet") and sends `n`. And `do_jump` moved the cursor with
    `nvim_win_set_cursor(0, …)` from inside a `vim.schedule`, where window 0 is
    whatever the user focused while the match's ancestors were being fetched —
    possibly not even a window on the browser buffer. It resolves a live window
    for that buffer first and skips the move when there is none. The same
    commit brought `expand_or_child`'s fetch in line with every other one: it
    passed a hard-coded `vim.fn.getcwd()` as the search dir, and that directory
    is what decides which `connections.json` the CLI reads.

47. **The DDL form sized itself from a guess about its own render**
    (`db_browser/forms_advanced.lua`, `c42646e`). `calc_height` walked the rows
    assuming one buffer line each, then added the preview's wrapped lines
    measured at the *outer* width; `render` emitted those rows at the *content*
    width, plus a blank separator before every section after the first, plus the
    shortcut bar and its two blank lines. The window was short by everything
    `calc_height` never counted — the separators, the preview's extra wraps, the
    bar — and the bar at the end was what got clipped, while in a multi-section
    form the focused row's highlight used the row index as a buffer line and sat
    on the line above the field the cursor was in. `render` now returns a
    `row → line` map it fills as it emits, and height comes from the lines it
    produced; `on_change` runs once per refresh instead of three times, so a
    preview whose text varies cannot size the window wrong. The shortcut bar
    wraps to the width it is drawn at — at 80 columns it was fitting by one
    character, and any narrower float simply lost `Space toggle`.
    `sql_db_browser_forms_focus_spec` (11) drives a real dialog for the height,
    the width and the highlight, and pins the mapping directly for a preview
    that would otherwise only be exercised through it.

48. **Two tables claimed to be the browser's line map**
    (`db_browser/init.lua`, `c134058`). `render_tree` did
    `line_to_node = new_map`; the actions' path did `util.set_line_map(ctx.line_to_node,
    new_map)` — in place, "so every holder of the table sees the same content".
    Contexts are handed to actions by reference and the search state keeps one
    across an async expand, so after any search-driven render the live table and
    the one every keymap reads were different: `i`, `y`, `x` and `gd` resolved
    the cursor's line against rows that were no longer on screen. Renders now
    sync in place only, and `refresh_by_conn` — which had its own copy of the
    render call, and so also skipped the statusline update — goes through the
    shared one. The same commit stops the multi-select cursor advance from
    trusting the stored `browser_win` (the keymap's own window is the one being
    tabbed through) and makes `M.close()` drop an active search, since the next
    open rebuilds the tree the matches pointed into and the match highlights
    stayed on the hidden buffer meanwhile. `sql_browser_line_map_spec` (4)
    asserts the identity across a render; reverting just that one line fails
    exactly two of its cases.

49. **A paste aimed at a sqlite table named that table as the connection**
    (`db_browser/init.lua`, `resolve_paste_target`, `b23c4cc`). The `p` keymap
    walks up from the node under the cursor to the enclosing database — or, for
    sqlite, to the connection that *is* the database — and then built the CLI
    argument from `target_db.meta.connection or node.name`. The fallback is only
    correct while the cursor is on the connection itself; sqlite trees hang
    tables directly off it, so `p` on one of those rows (or on a column below
    it) sent `--conn posts`, and the refresh in `on_complete` matched no root
    either, so a paste that worked left the tree stale. The walk-up already had
    the connection node in hand and kept only its dialect out of it. The
    resolution is now `resolve_paste_target(node, entry)`, which returns the
    whole target — the node, the connection *name*, the database, the dialect,
    the clone target — and `M._test` exposes it, since the keymap body needs a
    buffer, a yank register and a CLI to reach. `sql_browser_paste_target_spec`
    (7) covers the sqlite chain at all three depths, the two refusals (a table
    yank on a bare connection, an orphan node), and the dialect precedence;
    pointing that one expression back at `node.name` fails exactly the sqlite
    case.

50. **A `list` field's entries could not be edited at all**
    (`db_browser/forms_advanced.lua`, `5e043da`). The advanced form rendered an
    entry as a single summary line with a ▶/▼ marker. Three things made that
    line inert: the marker toggled `row.collapsed`, but rows are rebuilt from
    the entries on every structural change, so the flag was dropped again at
    once; `entry._summary` was initialised to the literal `"new entry"` and
    never recomputed, so the line it did draw could not change; and entries
    were never inserted into `focusable`, so Enter, Space and `d` skipped over
    them. `list` is the one field kind whose values the generated SQL reads —
    CREATE SCHEMA starts its Grants list empty, `a` adds an entry, and every
    value `gen_grant` needs comes from that entry's sub-fields, so the section
    was decorative: an added grant could only ever render `… TO ""`, since no
    grantee was nameable.
    An expanded entry now contributes one focusable row per sub-field this
    dialect has (`entry_subfield` honours the per-`dialect` markers
    `schema_create` sets), edited through the same text/select/multi_select/
    bool prompts as a top-level field, with the edited copy written back onto
    the entry in `refresh(row)` before anything reads it — the preview
    included. Folding lives on the entry (`_collapsed`) and is applied by
    `rebuild_rows()`, so the marker and the rows agree; `d` takes any row that
    belongs to an entry, resolving the index by identity when the row is a
    nested one; a new entry opens expanded and steals focus to its own first
    row; and the summary is computed from the entry as it renders.
    `sql_db_browser_entry_fields_spec` (13) drives this through the real
    dialog: buffer keymaps are collected from `nvim_buf_get_keymap` and called
    as functions (typeahead is not processed under `nvim -l`), with
    `vim.ui.input`/`vim.ui.select` stubbed, asserting through the `on_change`
    snapshots and the extmark that marks the focused row. It caught three
    assertions of its own on the way — `is_not.same` compares *deeply*, so two
    equal-looking privilege lists passed where identity was wanted, and
    `find(…, 1, true)` does not unescape `%[`. One existing case had to move:
    `sql_db_browser_forms_spec:42` pinned `entry._collapsed == true`, which is
    now the opposite of the intended default, and it pins the new value with
    the reason attached.

51. **The form's close-on-leave disarmed itself at the first pick list**
    (`db_browser/forms_advanced.lua`, `e13fd4e`). Its `WinLeave` autocmd carried
    `once = true` and a callback that declines to close while `editing` is set

## Round 14 — the completion trigger: what it pays for, and what it promises

Five commits, all in `completion/` (plus one debug command it feeds). This is
the path that runs on every keystroke inside a SQL buffer, so it got measured
before anything was changed: `resolve_current_context` costs 0.30 ms (full
buffer read, then the connection config, then an uncached `env.json` read plus
`vim.fn.environ()`), and one `context detect` subprocess costs ~3.6 ms warm and
~50 ms cold.

52. **The no-ctx branch read one character too many** (`completion/init.lua`,
    `407a534`). blink hands `cursor[2]` as a 0-indexed byte column, so
    `line:sub(1, col)` is the text left of the caret. When a caller passes no
    ctx the source fell back to `vim.fn.col(".")` — 1-indexed, and naming the
    character *at* the cursor — without dropping the one. So the two branches
    of one function disagreed: the fallback put the character under the caret
    into `line_before`, and therefore into the prefix, filtering the candidate
    list by a letter the user has not typed yet. Column completions for
    `…WHERE id|` came back narrowed to `i*` on one path and complete on the
    other. The `-1` is now explicit and the reason is in a comment beside it.
    `sql_completion_spec` section 5b (2 cases) pins the pair that used to
    diverge: no-ctx must equal the ctx path mid-word, and a ctx that carries a
    line but no cursor must be treated as no ctx.

53. **One completion resolved its buffer context four times** (`init.lua`,
    `feab149`). `get_dialect_flag` was called from `get_completions`, from
    `cache_key`, from `try_rust_context_async`, and from `get_items` — each a
    full buffer scan plus a connection lookup, and each against `vim.fn.line(".")`
    and the *current* buffer rather than the buffer and line the request is
    about. With two SQL windows that is a wrong-answer bug waiting for a
    background trigger, and on the way it is 4 × 0.30 ms of work that can
    disagree with itself (the cache key could carry a different dialect from
    the `--dialect` flag handed to the CLI). The dialect is now resolved once
    in `get_completions` and threaded through as a parameter, and the
    resolution is asked about the request's buffer and line; the data layer's
    `ensure_tables`/`ensure_columns` pair, which resolved the context twice
    per fetch, now resolve once and pass the result to `conn_key(ctx)`. Probe
    count for one trigger: `resolve_full_context` 4 → 1. Section 5d (2 cases)
    pins the arguments of the call instead of its count — a count assertion is
    what a caching layer legitimately changes, whereas "asked about the buffer
    the request is about, on the line the request is about" is the contract.

54. **The `-- @database` fallback wrote two spaces and had no tests**
    (`init.lua`, `714b82f`). Choosing a connection from the directive menu
    inserts a `-- @connection <name>` line plus a `-- @database ` line, parks
    the caret there, and feeds a literal space as a keystroke so blink
    reopens the menu on the trigger character. The written line *also* ended in
    a space, so every one of those insertions left `-- @database  ` on screen —
    and the async introspection that follows reads the directive's value.
    Neither `M:execute` nor `M.source:execute` had a single test: the pair is
    duplicated across the two, and the copies had already drifted (only the
    blink one preserved the line's indentation). One `insert_directive_pair`
    now serves both, the written line carries no trailing space, and
    `tests/sql/sql_completion_execute_spec.lua` (5 cases) covers the written
    lines and caret, indentation carry-over, both nvim-cmp entry shapes,
    snippet expansion, and the `default_impl` hand-off when nothing is typed.
    Restoring the trailing space fails exactly the two directive cases.

55. **`try_rust_context_async` was async in name only** (`init.lua`,
    `1cb1c2a`). It spawned the CLI and then called `obj:wait()`, so every cache
    miss blocked the editor for the spawn (3.6-50 ms, up to the CLI's 2 s
    timeout when it hangs) *inside* a function whose own comment said it was
    async, under a banner reading "Rust context detection via async
    vim.system". Worse, `wait()` is built on `vim.wait`, which Neovim forbids
    in a fast-event context: the call raised `E5560` there rather than
    parking, so a request made from an exit handler or a uv timer callback died
    without ever answering (confirmed by experiment: legal from the main loop,
    an autocmd callback and `vim.schedule`, illegal from `uv.check`). The
    result now reaches the caller through the process' exit handler, deferred
    one `vim.schedule` so the whole downstream pipeline — including the
    cache-miss introspection jobs — runs outside that context.
    `sql_completion_spec` section 5c (2 cases) pins both halves: a cache miss
    must return before the CLI has answered, and must still answer with items
    afterwards. The spec file needed real work first: ~40 of its cases assert
    immediately after the call, which only ever passed because of the freeze,
    so the three entry points are now wrapped once, at the top of the file, to
    pump the loop — which turns "the source never called back" into a named
    failure instead of a nil dereference several lines later.

56. **`:PosteDbDiag` reported no tables, ever** (`commands.lua`, `1cc2281`).
    `get_tables_and_alias` is declared over the Rust context and nothing else,
    but its signature carried two leading `_` parameters, so the debug command
    felt safe calling it as `get_tables(buf, cursor_lnum)` — leaving `rust_ctx`
    nil and the diagnostic printing `tables: {}` / `alias_map: {}` for a buffer
    full of FROM clauses. That is the one report whose job is to distinguish
    "context detection found nothing" from "the column cache is empty", and it
    could not. The dead parameters are gone (which also drops two
    `cursor_line or vim.fn.line(".")` expressions that pretended to matter),
    the command now runs the same context check the pipeline runs, and it
    prints `ctx_type` so a nil CLI is tellable from an empty statement.
    `get_tables_and_alias` itself gained a 3-case section 15: alias/schema
    mapping, nameless entries skipped, and the three-empty-containers contract
    the handlers index without guarding. The same commit removes two comments
    that still advertised a Lua heuristic fallback and a persistent context
    client, neither of which exists.

    files), up from 1577 by these 14; `luacheck` clean (245 / 246 files).

## Recorded, not changed (with rationale)

- **Completion still cannot be driven from a fast-event context**
  (`completion/init.lua:305`, round 14). Item 55 removed the illegal *wait*, but
  `get_completions` opens with `nvim_get_current_buf()`, which Neovim also
  forbids in a fast event (`E5560: nvim_get_current_buf must not be called in a
  fast event context` — reproduced), and the no-ctx branch reads the live
  cursor the same way. Fixing it means the caller telling us which buffer the
  request is about, and blink's context object carries line, cursor and syntax
  but no buffer. blink itself calls from an autocmd/scheduled path, so there is
  no reachable caller to fix this for; the probe that found it is in
  `sql_completion_spec` section 5c's neighbourhood and the constraint belongs
  in the provider notes if a caller ever needs it.
- **Six handler callbacks still resolve the connection key themselves**
  (`completion/handlers.lua:131, :143, :192, :254, :287, :375`, round 14).
  `data.conn_key()` with no argument re-runs the buffer walk (0.30 ms) on
  whichever buffer has focus, from inside an introspection flush. Item 53 fixed
  this on the synchronous leg, where it was both the latency and the
  wrong-buffer risk; on the flush leg each call is one more scan of a request
  that is already waiting on a subprocess, so the cost is invisible and the
  focus assumption is the same one every other callback in the module makes.
  The fix is to carry the resolved key through `handlers.dispatch`'s params
  table, which is a signature change across six handlers for work that a
  profile has not yet shown to matter.
- **`rust_raw` can be stale beside the context it produced**
  (`completion/init.lua`, `store_rust_context`, round 14). The debug dump's raw
  JSON is written only when the CLI runs, while `_ctx_cache` answers hits
  silently — so after two completions in one buffer, a dump can show the
  current context with the previous miss's raw text. Only reachable with
  `debug = true`, and fixing it means caching the raw string with the parsed
  context, i.e. holding every CLI response's JSON in memory.
- **nvim-cmp never sees the snippet items** (`M.source:complete` vs
  `M:get_completions`, round 14). blink appends `snippets.get_completion_items`
  after dedup; the cmp path returns deduped items and nothing else, and its
  `execute` has the snippet branch but nothing feeds it one. That asymmetry is
  almost certainly a bug, but the fix is not just the append: cmp needs the
  text-edit/`insertTextFormat` shape its `confirm` honours, and this harness has
  no typeahead, so neither cmp's expansion nor a regression in it is
  observable here. Item 54's spec pins what the cmp path does today (both entry
  shapes, through the shared insertion) so the difference is written down rather
  than silently relied on.
- **The context cache is FIFO, not LRU, and caps at 10**
  (`CTX_CACHE_MAX`, round 14). A hit does not move its key to the back, so ten
  distinct prefixes will evict the context you are still typing in. Left alone
  deliberately: the key carries `bufnr|changedtick`, so entries die with the
  next edit to that buffer, and insertion order evicts exactly the oldest —
  usually dead — keys first. A touch-on-hit would keep *live* keys longer and
  dead ones shorter, which is the opposite of what a 10-entry cap is for here.
- **Two triggers' debug fields can interleave** (`debug.begin()` on the calling
  tick, `debug.flush()` on the answer tick, round 14). Making item 55's wait
  asynchronous is what allows an overlap: with `debug = true`, a slow request
  can flush after a fast one has begun, so one dump carries both. The completion
  results themselves are per-request; only the debug buffer is shared.

- **`tree.render_tree` still takes two arguments it ignores** (`line_to_node`,
  `conn_label`, round 13). Item 48 made the map shared by identity through
  `util.set_line_map`, so the parameter that used to carry the map out of the
  renderer is now only a value the function never reads — it returns the new
  map instead — and `conn_label` has no reader at all, since the winbar comes
  from `update_winbar`. Both are still passed by every caller (`init.lua`:67
  and `util.render_tree`), which is exactly why they read as live. Dropping
  them touches both argument lists for no behavioural gain, with item 48's
  specs already pinning what the renderer must do.
- **Six browser mutations still hand-roll `util.refresh_subtree`** (`init.lua`
  :204, :467, :493, :505, :531, :542, round 13). Each repeats the invalidate →
  render → `async.fetch_children` → expand → re-render sequence with a
  *different* node in hand (a copy pipeline refreshes the clone's connection,
  then the target database, then the root). `refresh_subtree` takes one target,
  so folding them means either nesting callbacks inside the helper or giving it
  a list of targets. Left alone after item 49 removed the one copy that was
  actually wrong; `refresh_by_conn` (:925) is the model for the shape done
  right, since it invalidates locally and then calls the shared `render_tree`.
- **A reload replaces `root_nodes` instead of syncing it** (`init.lua`:644,

  for the line map, and reachable the same way (a search or paste that reloads
  while a callback holds a context). Not changed here because the fix is to
  reuse `util.set_line_map`'s in-place discipline for the roots, which needs a
  decision about whether a reload should ever be visible to an in-flight
  callback at all: the reloaded list is the correct one, so the stale render is
  a flicker rather than wrong data, and every site found today re-renders again

  `introspect/helpers.lua`:63 does for the column-info float — which is the

  is *not* settled is which of the two the editor should offer, so the picker
  stays as it is until a dialect is observed where choosing `<default>` inserts
  something wrong.
- **The root-word lookup misreads two families** (`poste-db.types`, round 12).

  bare literal — harmless, since neither `42` nor `'42'` is a range and the

  become a contract. The other direction is ClickHouse's `Nullable(Int32)`,
  whose root is `nullable`: a digit cell gets quoted, which ClickHouse casts on
  insert, so the visible cost is nil. Both are pinned in `sql_types_spec`.
  Widening the lookup (unwrap `Nullable(…)`, strip a `range` suffix) is a
  one-line change with no test today to say it was needed.
- **The editor's type table stays separate** (`editor/cell.lua TYPES`, round

  whose categories (date/json/uuid/editable) overlap the numeric one only by

  consulted with a *normalized* ctype that has no spaces or parentheses left.

  question twice.
- **An extra column in the file aborts the import instead of being dropped**

- **Completion caches columns under the identifier as typed**

- **A reference qualified by four or more names is checked against its leftmost

  matters (statement splitting, dangerous-keyword masking) is unaffected by

  they were added for, and resolution goes through `build_conn_url`, which

- **An integral float `port` needs no coercion** — `port = 5432.0` clears the
  validation added in `d6a39b4` (`tonumber` accepts it and it is integral),
  and concatenating the number into the URL yields `…:5432/…` because Neovim
  runs LuaJIT, which prints integral floats without the `.0`. A first attempt
  "fixed" this with `math.tointeger`, which does not exist in LuaJIT and broke
  19 specs; one new spec pins the rendering instead, since a 5.4 host would
  produce `postgres://h:5432.0/blog` from the same source. No production
  change — which is why it fails nothing when reverted.
- **`resolve_conflict_names`' rename dialog is unreachable** — its only
  production caller, `paste_objects` (`copy.lua:604`), passes
  `skip_dialogs = true`, so the `input_fn` prompt, its abort path and the

  them directly. `make_default_input` exists for a flow the browser dropped
  when paste became silent-by-default. Deleting it would leave the exported
  function without the `opts` branch it documents, so it is kept and recorded:
  either wire a "ask before renaming" option back into the paste confirm, or
  remove the branch with the dialog.
- **`catalog.routine_def_sql` (postgres) can fetch a different overload than
  the browser showed** — it filters `pg_proc` on `p.proname` alone and appends
  `LIMIT 1` with no `ORDER BY`, so with two schemas or two argument lists
  sharing a name the definition returned is whichever row the plan produces
  first. `view_definition_sql` right below it does the careful version
  (joins `pg_namespace`, excludes system schemas, prefers `public`). Fixing
  this properly means the caller must pass a schema (and argument types):
  `fetch_routine_definition` gets `{conn, db, dialect, name, rtype}`, and the
  `name`/`rtype` pair identifies a routine uniquely only for mysql. Recorded
  until the routine nodes carry a schema.
- **A pasted postgres routine keeps the source schema prefix** —
  `pg_get_functiondef` prints a fully qualified name (`public.foo`), and the
  rename substitutes only the last part, so pasting into a database whose
  schema is not `public` targets `public` anyway (or errors when it is
  absent). Same class as item 8, but the schema here comes from the server's
  text rather than from the browser's node, so the fix belongs with the
  routine node gaining a schema field (previous bullet).
- **`copy_ddl`'s mysql backtick scan is a loop that runs at most once** — the
  pair it tests first is `` `myschema` `` for a qualified name (or `` `root` ``
  inside a DEFINER clause), and when that is not the routine the second
  backtick is re-found from `close + 1`, which makes the `open > close` half of
  the "stop runaway scans early" test vacuously true; the other half,
  `open < kw_pos + 200`, then breaks. Only a second pair more than 200 columns
  past the keyword avoids the break — and that branch sets `open = nil`, so it
  ends the loop too. Either way the literal `` `src` `` fallback below is what
  rewrites a schema-qualified name. Structure, not behaviour: the output is
  correct for both pinned definitions, but the loop is really an `if` plus a
  fallback, and it reads as a scan that never happens.
- **`log_viewer.guess_table` cannot see a quoted identifier** — its patterns
  accept `[%w_]+` only, so `FROM "public"."orders"`, `` FROM `orders` `` and
  `FROM [orders]` all answer `nil`, while every statement the browser
  generates is quoted. Little surfaces today: the log column prefers the
  database name and no recorder sets `entry.table`, so the guess is a last
  resort. Fix it by reading an identifier (quote-aware, last dotted part) at
  the keyword rather than by widening six Lua patterns. Note also that its
  JOIN-before-FROM order is *pinned* by a spec (`posts JOIN comments` reports
  `comments`), so changing the preference is a behaviour decision, not a bug
  fix.
- **Pasting into clickhouse or mssql probes 100 names it cannot check** —
  `dialect_table_exists_sql` branches on mysql/mariadb, postgres, and
  everything else, and the everything-else SQL is SQLite's `sqlite_master`.
  So a paste targeted at a clickhouse or mssql connection asks a
  nonexistent catalog 100 times (bounded by item 7's cap), then gets
  `<name>_copy101`. Not fixed here because the probe is not the broken link:
  the copied DDL text is the source engine's own (`prepare_table_ddl` rewrites
  only the name), so a cross-engine paste fails at `CREATE` whatever the
  collision check returns — and `catalog.list_objects_sql` already refuses
  these dialects for the copy *source*, so only the target side is unguarded.
  A real fix means either translating DDL between engines or refusing
  unsupported paste *targets* up front in `show_paste_confirm`; the latter is
  a few lines and is the honest next step.
- **`export_to_clipboard` reports success it cannot see** — Round 9's test fix

  status: `provider#clipboard` runs pbcopy/win32yank through `s:try_cmd`, which
  on a non-zero exit only `echomsg`s and returns, so a lost pasteboard race
  leaves the user reading `Copied 1200 rows as CSV to clipboard` with nothing
  copied. Not fixed: the only signals available are reading `+` back (a second
  external call, and it costs a round trip per export) or
  `provider#clipboard#Error()`, which reports *no provider found* but not a
  copy that failed once one had resolved. Warning on that half would be
  honest, and `export_to_file` has the same shape for its path copy.
