## Bugs found but NOT fixed (with rationale)

- **`is_query_sql` substring `RETURNING` match** (`exec_run.lua:110`): a DML
  statement containing the word RETURNING anywhere (even in a string literal)
  is classified as a resultset; likewise the leading-keyword `gsub` misses
  comment/paren-prefixed statements. This only shifts classification in the
  tie-break case (driver reports `affected_rows` for a query); a correct fix
  needs statement-aware lexing, not a regex. Risk: cosmetic mis-render of the
  response type. Left alone to avoid churning a guarded heuristic.
- **`database_from_url`** (`session_conn.lua:36`): ignores `?query` params and
  breaks on `/` inside a password. Display/label only (the Rust side owns the
  real connection). Low risk, left alone.
- **`format.lua` `wrap_text`** byte-splits at `width`, which can split a UTF-8
  char in non-ASCII error messages. Error text is display-only; nvim renders
  replacement chars. Low risk.
- **`file_exec.lua` `close_progress`** is defined but never called — the
  completion path only re-renders the progress dialog and relies on the
  dialog's own `on_close`. The unused function suggests lost wiring ("allow
  close-on-finish"), but the dialog remains closable through its default
  bindings, so deleting/rewiring is a product decision, not a clear bug.
  (Audit rule: 0-hit grep alone does not justify deletion; left in place.)
- **`session.begin()` runs before the dirty-edit / DML-guard cancels** in
  `sql_runner.run_sql_request`, so a cancelled request still clears
  `last_response`/`last_dataset` (the latter only read by the AI chat context).
  Moving `begin()` below the guards would be slightly more correct, but the
  only casualty today is the AI "last dataset" context after a *cancelled* run
  — behavior change without test coverage, documented instead.
- **Pre-existing local WIP not touched**: the working tree carried uncommitted
  dialect work (`syntax.lua`, `ts_stmt.lua`, `buffer/nav.lua`, specs,
  LEARNINGS.md, connections.toml, playground). Per the preflight harness these
  were not committed and none of my fixes overlapped them.

## Architecture / code smells (documented, not refactored)

- **Undefined-global class of bugs** (findings 1-3, 10) all came from the same
  pattern: locals required inside one function and referenced in another.
  Remediation suggestion: keep the `luacheck` run in CI (`luacheck lua plugin
  ftplugin` — 0 errors, 51 mostly-benign warnings today) so
  "accessing undefined variable" fails the build instead of awaiting an audit.
- **`buffer/init.lua` `render_dataset` is ~230 lines** juggling layout vs
  legacy pagination, window (re)creation, window options, autocmd rotation and
  cursor placement. Suggested split: window-options application and the
  WinResized/VimResized/WinScrolled/WinClosed rotation deserve their own
  helpers (the rotation block already has a good comment — it just outgrew the
  function).
- **Duplicated render paths**: `render_dataset_legacy` (buffer/init.lua) and
  `page.refresh_page` legacy path both implement the padded_full page-slicing
  math with subtly different bookkeeping (`padded_full`/`meta_full` vs
  in-place mutation). The layout-aware path makes the legacy one deletable
  once no caller hits it — worth a deliberate removal pass (with the audit
  harness's grep discipline).
- **Duplicated USE detection**: `sql_runner.is_use_stmt` (plain only, routing),
  `exec_run.detect_use` (plain/quoted/comment, execution). The routing check
  is intentionally narrower (quoted USE goes to the session, which handles it
  persistently), but this deserves a comment cross-referencing the two so the
  next reader doesn't "unify" them blindly.
- **`db_browser/operations.lua` and `db_browser/copy.lua` carry most of the
  module-size tail** (1260/1207 lines) with form/confirm/batch-job logic
  interleaved — the audit harness's "one module, one job" split applies, but
  that is a dedicated refactor session.
- **`statement.lua` dead loop** (luacheck: `has_sql is never accessed`): the
  comment-only detection loop computes `has_sql` and then a *different*
  helper (`has_sql_content`) is checked. One of the two should go; the loop is
  the dead one, but removal should ride a dedicated cleanup with the full
  suite (audit-harness rule).
- **`nav_raw.toggle = M.show`** does not toggle; repeated invocations stack
  floating windows until each is closed with `q`. Consider tracking the open
  raw window (like `nav.preview_cell` does with `preview_win`).
- **`file_exec.run` builds the job command via a shell string**
  (`vim.fn.shellescape` assembly) while `exec_run` uses an argv list via
  `cli.run_async`; the list form avoids quoting-class bugs and should be the
  single pattern.
