## Fixes (each with tests)

- **`format.format_error` crashed on a non-string error.** The seam
  sits below `verdict.error_text`, whose structured branch
  (`vim.inspect`) guards the `classify` path — but
  `response.handle_error` forwards its *raw* message here too, and a
  non-string there raised inside `wrap_text` (`#text` on a number,
  `text .. "\n"` on a table). Reached by the probe sweep with
  `format_error({ ... })` / `format_error(42601)`; on every current
  path the message is a string, so this is defense-in-depth — but it
  is the same non-string-error family round 44 fixed in the
  db_browser summaries, and the inconsistent twin proved the intent:
  `handle_error` already wrapped `state.last_error.message` in
  `tostring` while passing the untouched original to `format_error`.
  The seam now normalizes: `nil`/`vim.NIL` render as an empty message,
  anything else as `vim.inspect`, and the DSN redaction runs over the
  normalized text (pinned by a spec that a structured error's inspect
  output still gets redacted). The redis plugin's `format.format_error`
  already does `tostring(err or ...)` — this was the family's last
  survivor.

## Probed, held (throwaway spec, not committed)

- **`lex` / `statement` / `dml_guard` / `verdict` / `toml` / `width`**
  against unterminated quotes, `$tag$` pairs, nested block comments,
  10k-statement files, BOM+`USE`, NUL bytes, `2^53`/`-1` affected
  counts, `vim.NIL` errors, TOML's pathological headers
  (`[a]]`, `[[a]`, duplicate headers, 10k-section files) — every call
  returned a value or a `(nil, err)` pair, never raised.
- **`import/format.parse_csv`** — RFC-4180 hostile shapes (stray
  mid-field quote, CRLF inside quotes, duplicate headers, ragged rows,
  100 KB cells) all fail closed with a readable error or parse
  rectangular. The probe initially "failed" everything because it
  assumed a `(header, rows)` return; the real contract is one
  `{ columns, rows }` table or `(nil, err)`.
- **`import/mapping.coerce_value`** takes the *type name string* (the
  probe passed the column table and got the resulting
  `lower on nil`-shaped errors — probe bug, not a code bug; production
  callers pass `table_col.col_type`).
- **`export.format_json` on NaN/Infinity raises**
  (`vim.json.encode` refuses non-finites). Audited, **not fixed**: the
  value path from the binary can never carry a raw non-finite —
  `poste-exec/sql_values.rs` spells them as their engine text
  (`"NaN"`, `"Infinity"`), pinned on the Rust side
  (`float_json_keeps_the_non_finite_values_as_their_engine_spelling`,
  `an_infinite_real_reaches_the_wire_as_text_not_null`). A guard here
  would be dead code; recorded so the next "why does export crash on
  infinity" question has an answer: it can't happen from the wire, and
  if a future transport ever forwards raw doubles, `sql_values.rs` is
  the seam that must keep spelling them.
