## Bugs fixed

1. **The second `a` in a list was a silent no-op** (`db_browser/forms_advanced.lua`,
   `04d0def`). `a` was bound to `edit_current()` behind a check for
   `row.type == "field" and row.field.kind == "list"`, i.e. it acted only when the
   cursor sat on the list's *own* row. But adding an entry moves the cursor onto
   the new entry row — that is what `add_list_entry`'s `focus_idx` hunt does — so
   the first press worked and every later one did nothing, with no message and no
   visual change. A user filling in three GRANT entries had to walk back up to the
   `Grants:` line between each.
   `d` never had this problem: `delete_list_entry` resolves the list as
   `row.list_field or row.field`, so it works from the entry row and from a nested
   sub-field row. `a` now takes the same lookup, and the two share the extracted
   `add_list_entry()` so the `<CR>`-on-list-row path and the `a` path cannot drift.
   Pinned by three tests in `sql_db_browser_entry_fields_spec`: `a` again from
   inside the entry adds a second entry, `a` lands the cursor on what it added, and
   `d` deletes the entry under the cursor rather than the first one.
2. **`a` and `d` were bound but never shown** (same file, round 19). The shortcut
   bar came from a fixed six-entry list (`q y s j/k Enter Space`), so the `list`
   field kind — the one that generates the GRANT/`WITH GRANT OPTION` entries — had
   no discoverable keys at all. `footer_lines` takes a `has_list` flag now and
   appends `{a add item} {d del item}`; the flag comes from `has_list_field(rows)`,
   i.e. from the *rendered rows*, not from the section spec, because `build_rows`
   drops the fields of a collapsed section and a list nobody can reach should not
   be advertised either. Forms without a list still show six entries, so the bar
   does not start lying about keys that do nothing there.

3. **`ident.quote` rewrote the names of real objects** (`ident.lua`, `a3cc8a9`).
   It split on `.` and quoted each part, so a table actually named `staging.v1`
   — legal in Postgres and MySQL, and introspected by the browser under exactly
   that name — became `"staging"."v1"`. Every statement built from it then
   addressed a different object: `DROP TABLE "staging"."v1"`,
   `UPDATE "public"."staging"."v1"`, and a rename whose new name contained a dot
   moved the table into a schema (`ALTER TABLE … RENAME TO "v1"."2"`), which the
   generator's own doc comment says a rename must not do.
   I inventoried every call site before changing anything (~40 sites across
   `dml`, `export`, `table_ops`, `db_browser/{operations,ops_sql,ops_drop,schema_create,db_create,copy,copy_ddl}`):
   all of them pass a name that introspection reported, or one plain name typed
   into a prompt. Two inputs really are references: the sequence name parsed out
   of copied DDL (`copy_ddl`, whose comment had to say "quote() splits on the
   dot" for the code to make sense) and the `Name` field of the New Table form.
   So the split did not go away, it moved: `M.quote` now always means one
   identifier, and `M.quote_ref` is the splitting one, used by those two callers.
   While wiring the second one up I found the form's own bug — it prepended the
   browsed schema unconditionally, so typing `analytics.events` under that schema
   produced `"analytics"."analytics"."events"`, a table that does not exist. The
   prepend is now guarded by `M.is_qualified`, which answers with the *same*
   predicate `quote_ref` uses to decide whether to split: testing for a dot with
   `find` would have disagreed for `my..table`, where no split happens but the dot
   check says it did, and the schema prefix would be dropped.
   Pinned by 14 net new tests (19 added, 5 pinned the old split directly and moved
   to `quote_ref` or went away with the guard): `quote` keeps a dotted name whole
   in all four dialects and still escapes the dialect's quote char inside it; a
   new `quote_ref` describe holds the relocated assertions plus per-part escaping;
   `is_qualified` is pinned both ways; DML keeps a dotted table *and* a dotted
   column one identifier; the rename generator keeps dots in both the target and
   the source; and four for `new_table_ref`, extracted from the form callback into
   a tested helper.
4. **`extract_table_name` mis-read the table it was pointing at** (`statement.lua`,
   `056a9a3`). The one place that has to guess a name from *typed text* — running
   SQL from a buffer, where there is no browser node to ask — did it by matching
   `FROM%s+(%S+)` against an upper-cased copy of the statement and then trimming
   the match: quote characters off both ends, punctuation off the tail, and the
   text before the first `.` dropped. Three consequences, all silent:
   `FROM "Order Items"` gave `order` (`%S+` stops at the space, and `order` is a
   name that can exist), `FROM "staging.v1"` gave `v1` (the dot inside the quotes
   is not a separator — round 21's bug, reached from the other side), and
   `FROM "Users"` gave `users`, because the whole reference was matched in
   `upper` and lower-cased on the way out, which is what a quoted name must never
   lose. The same trimming also handed the DML builder `users,orders` for
   `FROM users,orders` and `(select` for `FROM (SELECT 1) x`.
   It now takes only the *offset* of the reference from the pattern (`FROM%s+()%S+`,
   an empty capture — LuaJIT's `find` returns captured strings, not capture
   positions, so `(%S+)` could not be turned into an offset into `clean` the way
   it can on 5.2+; noted in the code because it reads like a typo) and then reads
   the original-cased text back from there, one identifier at a time: quoted names
   end at their own closing quote, a doubled closing char is the escape and stays
   in the name (collapsed once), a bare name ends at the first character that
   cannot belong to it, and the chain continues across a dot. Only the last part
   is kept — the qualifier in front of it is not resolvable from text (`db.tbl` and
   `schema.tbl` look identical) and the dataset layout carries the schema separately.
   Where the reference cannot be resolved the answer is `nil`, which is what a 2+
   JOIN query already returns: the dataset header drops the table name and the
   status line labels the tab `result n` (`buffer/nav_ui.lua:95,177`). The nil
   path is taken by a subquery in the table position, a dangling dot (`users.`,
   `.hidden`), and now a comma sibling — the 2+ JOIN guard could not see
   `FROM a, b` at all, so a two-table list used to name whichever table was
   written first, and the DML would edit that one.
   Pinned by 11 tests in `sql_statement_spec` (30 → 41).
5. **A result set with no table still produced a batch of DML** (`dml.lua`,
   `2f1fca8`). Round 22 left a question open — what does `nil` from
   `extract_table_name` *lead to*? — and the answer was not what the prose around
   it assumed. `generate_dml` reads `tab.layout.table_name or ""`, and the three
   generators interpolate `quote_schema(schema) .. ident.quote(table_name)`, where
   `ident.quote("")` is `""`; so an empty name produced
   `UPDATE "blog". SET "x" = 1 WHERE "id" = 7;`, `INSERT INTO "blog". (…) VALUES (…)`,
   `DELETE FROM "blog". WHERE …` — a dangling dot from the schema prefix. Measured
   with a throwaway probe spec rather than inferred (the probe is gone; the exact
   strings are in the Verified list below). Nothing was written wrongly — the
   server rejects the syntax — but the user saw a parser error for *every* row of
   the batch, and no message pointed at "this result set has no table". It now
   refuses once, before any statement is built, with a reason that
   names the cause and the way out (the browser is the path that always knows the
   table), and only when an edit is actually pending: with none, "No changes to
   commit" remains the truth instead of a warning about a missing name nobody was
   asking about.
   The commit warning's own header was part of the same confusion —
   `"Skipped N edit(s) — no safe WHERE target:"` was hard-coded to the one reason
   that existed when it was written, so it mis-described any other refusal the
   generator added later. It reads `"Some edits were not committed:"` now and lets
   each line carry its reason, which also keeps the count honest: a whole-batch
   refusal is one line, not one per edit.
   The guard sits in `generate_dml` rather than in each generator because that is
   the editor's only entry (round 17 established this for `allow_expr` too), and
   `import/execute.lua`, the one other caller of `generate_insert`, gets its table
   from the picker and cannot supply an empty name. Pinned by 3 tests in
   `sql_dml_spec` (24 → 27).
6. **A non-finite number in a committed cell became the word `inf`**
   (`ident.lua`, `dml.lua`, `14ebedc`). `format_value`'s numeric branch asks
   `val == math.floor(val)` first, and `math.floor(math.huge) == math.huge`, so an
   infinite value took the `%.0f` path and `string.format("%.0f", math.huge)` is
   `"inf"` — emitted bare, i.e. `UPDATE "t" SET "x" = inf WHERE "id" = 1;`, which
   the red run printed verbatim before the fix. `quote_literal`'s number branch had
   the same hole for a non-integral infinity (`tostring(math.huge)`), so the two
   agreed on the wrong answer. `quote_literal` now renders the three values as the
   literals postgres prints and parses (`'Infinity'`, `'-Infinity'`, `'NaN'`) and
   `format_value` delegates to it through `ident.is_non_finite`, which is checked
   *before* the integral test. ClickHouse keeps the bare `inf` / `nan` it spells
   as literals — that is what the old code already sent it, so nothing moved for
   that dialect. 8 tests: 3 in `sql_ident_spec` (35 → 38), 4 in `sql_dml_spec`
   (27 → 31), and one pin in `sql_editor_spec` (138 → 139) for where the number
   comes from at all: `parse_value("Infinity")` returns a number, because
   LuaJIT's `tonumber` accepts that spelling — which is also why this half had to
   ship with the binary's half (`08acb28`), not after it.
7. **One `Infinity` row un-aligned its whole column** (`format.lua`, `b8acb90`).
   Round 24's other consequence: the value is text on the wire now, and
   `is_numeric_column` — the check that decides right-alignment — accepts a
   string only when it matches `^%-?%d+%.?%d*$`. `"Infinity"` does not, so a
   `float8` column with one infinite row lost the alignment its declared type
   asks for, and ClickHouse's float columns (always text) lost it on `inf` /
   `nan` too. `is_non_finite_text` now whitelists the two spellings the engines
   print, case-folded, and only for a column `types.is_numeric` already claimed
   — a `text` column full of `"Infinity"` strings is still text. 3 tests in
   `sql_format_bigint_spec` (5 → 8): the postgres spelling, the ClickHouse
   spellings, and the text-column guard that keeps the exemption from widening.
8. **A filter left a live search pointing at rows it had removed** (`buffer/search.lua`,
   `38d0860` and `970b3d9`). `compute_matches` records each hit as a *view position* (`row =
   view_pos`), and `filter_by_current_cell` rebuilds `view_indices` from
   `filtered_indices` — so after filtering, `search_matches` still held the
   pre-filter positions while the buffer showed something else entirely. Only the
   count was measured (the new spec's first assertion), but everything downstream
   reads that same list: the winbar's `i/n`, `apply_search_highlights`' row tinting,
   and `n`/`N`, where a position past the filtered view hits
   `jump_to_search_match`'s `if not match then return end` and the key just stops
   responding.
   `recompute_after_view_change` exists for this exact hazard — its own comment says
   matches are stale "after sort/filter" — and the sort path (`nav.lua:276`) calls it
   after every re-render; the filter path rendered and returned. One call added, and
   4 tests in the new `sql_buffer_search_view_spec`. The third and fourth pass at
   `HEAD` on purpose: `clear_filter_search` already drops the state, and the n/N
   walk itself was never broken — both are behaviour the fix must not disturb.

## Test-infrastructure findings

- **The spec process inherits the developer's Neovim config, and that changes
  measurements** (round 20). plenary starts each spec file in a *child* nvim
  without `-u` — the fact `tests/minimal_init.lua` already notes for
  `$POSTE_BINARY` — so `~/.config/nvim/init.lua` runs there. On this machine it
  sets `number` and `breakindent`, which is what turns the 77-column bar into 79
  cells: `number` narrows the wrap width under the line, and `breakindent` counts
  the leading blanks a second time for the continuation row. Any assertion about a
  line that nearly fills its float is therefore machine-dependent while it uses
  `strdisplaywidth`. `:verbose set breakindent?` in the spec child is the quick
  way to see this.
- **I tried to fix the leak and backed it out** (round 20). Redirecting
  `XDG_CONFIG_HOME` in both runners makes the spec child hermetic — measured:
  `number=false breakindent=false tabstop=8`, and the bar measures 77 — but it also
  removes the Tree-sitter `sql` parser that the same config installs. The gate went
  from 1595 to 1468 successes and 3 failures, all four deltas in
  parser-dependent specs: `sql_ts_stmt_spec` 108 → 1, `sql_multi_stmt_spec` 38 → 34,
  `sql_semantic_diagnostics_spec` 20 → 7, `sql_statement_indicator_spec` 8 → 5.
  124 of those tests *vanished from the tally* rather than failing: the specs guard
  a whole `describe` on `ts_stmt.check_parser()` and fall back to a single
  `pending` test. That is the same skip-by-absence shape round 18 removed from the
  binary guard, ~124 tests wide, and it is why the runner change is not in this
  commit. A hermetic gate needs the parser installed by the harness, not a config
  borrowed from the developer.
- **One parser-dependent spec had the worst of both patterns** (round 20, fixed).
  `sql_statement_indicator_spec`'s boundary `describe` had no guard at all: in a
  parser-less environment three tests fail on extmarks that can never appear, and
  the fourth — `does not paint single-line statements`, asserting *zero* extmarks —
  passes vacuously for the same reason. It now wraps all four in
  `it_needs_parser`, using the plugin's own `check_parser()` predicate, verified

## Recorded, not changed (with rationale)

- **An `if` whose then-branch is empty, with a lint waiver on it** (`buffer/init.lua:615`,
  round 26). `if tab.is_sorting then -- luacheck: ignore 542 else tab.sort = nil … end`
  encodes "only reset the sort when this render is not the sort's own re-render", and
  reads as a mistake every time someone opens the file — the inverted form
  (`if not tab.is_sorting then`) is the same behaviour without the empty branch. Left
  alone because touching `render_dataset`'s state resets is how rounds 21–23 found
  bugs elsewhere, and this one is cosmetic; it is the kind of change to make with a
  failing test that pins `tab.sort` surviving a sort re-render, not on the way past
  something else.
- **What round 22 deliberately left on the table** (`statement.lua`). Three
  residuals in the text fallback, each one cheaper to record than to design around:
  a **bare** mixed-case name still folds to lower case (`UPDATE Users` → `users`),
  because `read_identifier` has no dialect argument. A dialect *is* reachable at
  both call sites (`parsed.dialect` in `response.lua`, `tab.layout.dialect` in
  `edit_commit`), so the plumbing is small — what is not settled is the rule to
  plumb in: postgres and MariaDB fold unquoted identifiers, MySQL depends on
  `lower_case_table_names`, ClickHouse and MSSQL on collation, so a dialect-keyed
  fold would be a guess for three of the engines this plugin drives. The case
  where the intent is unambiguous — a *quoted* name — is the one this round fixed,
  and a name typed bare is the one the server itself may resolve loosely;
  the **qualifier** of
  `schema.tbl` typed in text is dropped, which is right for the dataset layout
  (it stores the schema separately) but means a buffer query that relies on an
  explicit schema different from the connection's default cannot express it here;
  and a **CTE** name comes back as the table (`WITH t AS (…) SELECT * FROM t` →
  `t`), since resolving it needs statement structure this helper does not have.
  All three are pinned by tests (`keeps the case of a quoted name, and folds an
  unquoted one`, `keeps only the last part of a three-part reference`,
  `still hands back a CTE name (recorded limitation)`) so the behaviour is written
  down in the suite, not just here.
  Correcting round 21's note on this line: it claimed the lowercasing "is also
  consumed by completion and semantic diagnostics". It is not — a call-site grep
  (`statement.extract_table_name`) finds only `sql_runner/response.lua`,
  `edit_commit/init.lua` and the two test stubs, and completion has its own
  parser path. That claim was inherited from an assumption instead of a grep, which
  is the reason the fix looked bigger than it was for a round.
- **The generators still take any name they are given** (`dml.lua:135,168,188`).
  Round 23's guard is in `generate_dml`, the batch entry the editor uses, not in
  `generate_update` / `generate_insert` / `generate_delete`: called directly with
  `""` they still emit `UPDATE "public". …`. That is deliberate — the only other
  caller (`import/execute.lua`) provably has a name, and a second layer of refusal
  would need a `nil` return threaded through the import chunk loop for a case that
  cannot occur. Worth revisiting if a third caller appears.
- **`footer_lines` measures the bar in bytes, not cells** (`forms_advanced.lua:219`).
  Correct today — the six (eight) entries are fixed ASCII literals — and the
  comment above the function says so. It would break the first time someone adds a
  CJK label to `FOOTER`; the fix is one `strwidth` call, but doing it now would
  paper over the fact that `FOOTER` is a UI string table with no translation path.
- **`opts.height` still truncates below the fold.** A form taller than
  `opts.height or 40` scrolls, so on a long CREATE TABLE the shortcut bar can sit
  below the visible area with no hint that there is more. The bar is painted by
  `render` either way; making the float reserve its two-plus lines is a separate
  geometry change and needs its own test against `height_for`.
- **The `strwidth`/`strdisplaywidth` split is a rule for future assertions, not a
  sweep.** `sql_db_browser_forms_focus_spec.lua:93` still asserts
  `strdisplaywidth(line) <= 58` on the wrapped bar. It is safe because 58 is well
  under any window's wrap width, so no continuation row is counted; converting it
  would be churn with no failing case behind it.
- **CI cannot gate on the Lua suite either way** (round 18, unchanged).
  `.github/workflows/ci.yml` builds no Rust binary and wraps `./tests/run.sh` in
  `|| echo "::warning::…"`, so a red Lua suite is a warning and a green one proves
  little; luacheck is the only hard gate. With round 18's guards in place a real
  failure gate is now *possible* — the Rust-dependent tests skip with a printed
  reason instead of failing — but the ~124 parser-dependent tests above are the
  remaining blocker, so the workflow is left alone.
- **The dummy binary stays** (`minimal_init.lua:18-24`). It exists to keep the
  vendored installer from downloading during headless runs; `find_poste_binary()`
  only checks readable + executable, so it cannot tell the dummy apart, which is
  precisely why round 18's guard probes behaviour (`context detect`) instead of
  presence.
- **What round 24 did not check about the values it now writes** (`ident.lua`).
  The specs assert the emitted text; no server was contacted, so "`'Infinity'` is
  what postgres parses back" and "ClickHouse takes bare `inf`" rest on those
  engines' own documented spellings — and the ClickHouse branch is the old
  behaviour, untouched, so the worst it can do is stay wrong in the way it already
  was. Two neighbours of the fixed path also went unmeasured: `validate_value`'s
  interception of a numeric column handed the text `Infinity`, and `format.lua`'s
  rendering of it — reading both suggested the string branch handles them, but
  neither is asserted anywhere. Round 25 measured the second one and it did not:
  the *text* rendering is fine (the string branch prints `Infinity` verbatim), but
  the alignment check next to it treated that text as non-numeric, which is now
  bugs-fixed item 7. `validate_value`'s interception is still unasserted.
- **The display helpers still print the bare Lua spellings** (`format.lua`
  `format_number`, `nav_cell.pretty_print` / `clipboard_text`, round 25). Probed
  directly: each renders a non-finite *number* as `inf` / `-inf` / `nan`, not as the
  `Infinity` / `NaN` the engines print. Reachable one way: `editor/nav.lua:93` puts
  an edit's parsed value into `tab.layout.rows`, so typing `Infinity` into a cell
  previews it as `inf` while the committed row will read `Infinity`. Not changed:
  the correct preview is dialect-dependent — ClickHouse's rows really do carry bare
  `inf` — and `cell_to_string` has no dialect to ask. Passing one down for this
  alone is a wider change than the mismatch is worth; a number in the *wire* path
  is impossible since `08acb28`, so only a typed edit can reach it.
- **The value converters are still two families** (`poste.nvim`
  `sql_values.rs` vs `sql_executor/*/value.rs`, round 24). Only the float rule is
  shared now; the rest of the per-dialect decoding remains duplicated between the
  plugin's executor and the CLI's session/exec-file paths, with a header comment
  asking the two to stay in sync. Unifying them is a real refactor and the drift
  that actually caused a bug was this one rule, so the layout stayed.
