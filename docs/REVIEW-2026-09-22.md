## Bugs fixed

1. **The second `a` in a list was a silent no-op** (`db_browser/forms_advanced.lua`,
   `04d0def`). `a` was bound to `edit_current()` behind a check for
   `row.type == "field" and row.field.kind == "list"`, i.e. it acted only when the
   cursor sat on the list's *own* row. But adding an entry moves the cursor onto
   the new entry row — that is what `add_list_entry`'s `focus_idx` hunt does — so
   the first press worked and every later one did nothing, with no message and no
   visual change. A user filling in three GRANT entries had to walk back up to the
   `Grants:` line between each.
   `d` never had this problem: `delete_list_entry` resolves the list as
   `row.list_field or row.field`, so it works from the entry row and from a nested
   sub-field row. `a` now takes the same lookup, and the two share the extracted
   `add_list_entry()` so the `<CR>`-on-list-row path and the `a` path cannot drift.
   Pinned by three tests in `sql_db_browser_entry_fields_spec`: `a` again from
   inside the entry adds a second entry, `a` lands the cursor on what it added, and
   `d` deletes the entry under the cursor rather than the first one.
2. **`a` and `d` were bound but never shown** (same file, round 19). The shortcut
   bar came from a fixed six-entry list (`q y s j/k Enter Space`), so the `list`
   field kind — the one that generates the GRANT/`WITH GRANT OPTION` entries — had
   no discoverable keys at all. `footer_lines` takes a `has_list` flag now and
   appends `{a add item} {d del item}`; the flag comes from `has_list_field(rows)`,
   i.e. from the *rendered rows*, not from the section spec, because `build_rows`
   drops the fields of a collapsed section and a list nobody can reach should not
   be advertised either. Forms without a list still show six entries, so the bar
   does not start lying about keys that do nothing there.

3. **`ident.quote` rewrote the names of real objects** (`ident.lua`, `a3cc8a9`).
   It split on `.` and quoted each part, so a table actually named `staging.v1`
   — legal in Postgres and MySQL, and introspected by the browser under exactly
   that name — became `"staging"."v1"`. Every statement built from it then
   addressed a different object: `DROP TABLE "staging"."v1"`,
   `UPDATE "public"."staging"."v1"`, and a rename whose new name contained a dot
   moved the table into a schema (`ALTER TABLE … RENAME TO "v1"."2"`), which the
   generator's own doc comment says a rename must not do.
   I inventoried every call site before changing anything (~40 sites across
   `dml`, `export`, `table_ops`, `db_browser/{operations,ops_sql,ops_drop,schema_create,db_create,copy,copy_ddl}`):
   all of them pass a name that introspection reported, or one plain name typed
   into a prompt. Two inputs really are references: the sequence name parsed out
   of copied DDL (`copy_ddl`, whose comment had to say "quote() splits on the
   dot" for the code to make sense) and the `Name` field of the New Table form.
   So the split did not go away, it moved: `M.quote` now always means one
   identifier, and `M.quote_ref` is the splitting one, used by those two callers.
   While wiring the second one up I found the form's own bug — it prepended the
   browsed schema unconditionally, so typing `analytics.events` under that schema
   produced `"analytics"."analytics"."events"`, a table that does not exist. The
   prepend is now guarded by `M.is_qualified`, which answers with the *same*
   predicate `quote_ref` uses to decide whether to split: testing for a dot with
   `find` would have disagreed for `my..table`, where no split happens but the dot
   check says it did, and the schema prefix would be dropped.
   Pinned by 14 net new tests (19 added, 5 pinned the old split directly and moved
   to `quote_ref` or went away with the guard): `quote` keeps a dotted name whole
   in all four dialects and still escapes the dialect's quote char inside it; a
   new `quote_ref` describe holds the relocated assertions plus per-part escaping;
   `is_qualified` is pinned both ways; DML keeps a dotted table *and* a dotted
   column one identifier; the rename generator keeps dots in both the target and
   the source; and four for `new_table_ref`, extracted from the form callback into
   a tested helper.
4. **`extract_table_name` mis-read the table it was pointing at** (`statement.lua`,
   `056a9a3`). The one place that has to guess a name from *typed text* — running
   SQL from a buffer, where there is no browser node to ask — did it by matching
   `FROM%s+(%S+)` against an upper-cased copy of the statement and then trimming
   the match: quote characters off both ends, punctuation off the tail, and the
   text before the first `.` dropped. Three consequences, all silent:
   `FROM "Order Items"` gave `order` (`%S+` stops at the space, and `order` is a
   name that can exist), `FROM "staging.v1"` gave `v1` (the dot inside the quotes
   is not a separator — round 21's bug, reached from the other side), and
   `FROM "Users"` gave `users`, because the whole reference was matched in
   `upper` and lower-cased on the way out, which is what a quoted name must never
   lose. The same trimming also handed the DML builder `users,orders` for
   `FROM users,orders` and `(select` for `FROM (SELECT 1) x`.
   It now takes only the *offset* of the reference from the pattern (`FROM%s+()%S+`,
   an empty capture — LuaJIT's `find` returns captured strings, not capture
   positions, so `(%S+)` could not be turned into an offset into `clean` the way
   it can on 5.2+; noted in the code because it reads like a typo) and then reads
   the original-cased text back from there, one identifier at a time: quoted names
   end at their own closing quote, a doubled closing char is the escape and stays
   in the name (collapsed once), a bare name ends at the first character that
   cannot belong to it, and the chain continues across a dot. Only the last part
   is kept — the qualifier in front of it is not resolvable from text (`db.tbl` and
   `schema.tbl` look identical) and the dataset layout carries the schema separately.
   Where the reference cannot be resolved the answer is `nil`, which is what a 2+
   JOIN query already returns: the dataset header drops the table name and the
   status line labels the tab `result n` (`buffer/nav_ui.lua:95,177`). The nil
   path is taken by a subquery in the table position, a dangling dot (`users.`,
   `.hidden`), and now a comma sibling — the 2+ JOIN guard could not see
   `FROM a, b` at all, so a two-table list used to name whichever table was
   written first, and the DML would edit that one.
   Pinned by 11 tests in `sql_statement_spec` (30 → 41).
5. **A result set with no table still produced a batch of DML** (`dml.lua`,
   `2f1fca8`). Round 22 left a question open — what does `nil` from
   `extract_table_name` *lead to*? — and the answer was not what the prose around
   it assumed. `generate_dml` reads `tab.layout.table_name or ""`, and the three
   generators interpolate `quote_schema(schema) .. ident.quote(table_name)`, where
   `ident.quote("")` is `""`; so an empty name produced
   `UPDATE "blog". SET "x" = 1 WHERE "id" = 7;`, `INSERT INTO "blog". (…) VALUES (…)`,
   `DELETE FROM "blog". WHERE …` — a dangling dot from the schema prefix. Measured
   with a throwaway probe spec rather than inferred (the probe is gone; the exact
   strings are in the Verified list below). Nothing was written wrongly — the
   server rejects the syntax — but the user saw a parser error for *every* row of
   the batch, and no message pointed at "this result set has no table". It now
   refuses once, before any statement is built, with a reason that
   names the cause and the way out (the browser is the path that always knows the
   table), and only when an edit is actually pending: with none, "No changes to
   commit" remains the truth instead of a warning about a missing name nobody was
   asking about.
   The commit warning's own header was part of the same confusion —
   `"Skipped N edit(s) — no safe WHERE target:"` was hard-coded to the one reason
   that existed when it was written, so it mis-described any other refusal the
   generator added later. It reads `"Some edits were not committed:"` now and lets
   each line carry its reason, which also keeps the count honest: a whole-batch
   refusal is one line, not one per edit.
   The guard sits in `generate_dml` rather than in each generator because that is
   the editor's only entry (round 17 established this for `allow_expr` too), and
   `import/execute.lua`, the one other caller of `generate_insert`, gets its table
   from the picker and cannot supply an empty name. Pinned by 3 tests in
   `sql_dml_spec` (24 → 27).
6. **A non-finite number in a committed cell became the word `inf`**
   (`ident.lua`, `dml.lua`, `14ebedc`). `format_value`'s numeric branch asks
   `val == math.floor(val)` first, and `math.floor(math.huge) == math.huge`, so an
   infinite value took the `%.0f` path and `string.format("%.0f", math.huge)` is
   `"inf"` — emitted bare, i.e. `UPDATE "t" SET "x" = inf WHERE "id" = 1;`, which
   the red run printed verbatim before the fix. `quote_literal`'s number branch had
   the same hole for a non-integral infinity (`tostring(math.huge)`), so the two
   agreed on the wrong answer. `quote_literal` now renders the three values as the
   literals postgres prints and parses (`'Infinity'`, `'-Infinity'`, `'NaN'`) and
   `format_value` delegates to it through `ident.is_non_finite`, which is checked
   *before* the integral test. ClickHouse keeps the bare `inf` / `nan` it spells
   as literals — that is what the old code already sent it, so nothing moved for
   that dialect. 8 tests: 3 in `sql_ident_spec` (35 → 38), 4 in `sql_dml_spec`
   (27 → 31), and one pin in `sql_editor_spec` (138 → 139) for where the number
   comes from at all: `parse_value("Infinity")` returns a number, because
   LuaJIT's `tonumber` accepts that spelling — which is also why this half had to
   ship with the binary's half (`08acb28`), not after it.

   asks for, and ClickHouse's float columns (always text) lost it on `inf` /

   `sql_format_bigint_spec` (5 → 8): the postgres spelling, the ClickHouse
   spellings, and the text-column guard that keeps the exemption from widening.

9. **A text column's digits, `true` and JSON stopped being its own text**
   (`editor/cell.lua`, `editor/nav.lua`, `be72542`). `parse_value` decided a value's
   type from the typed text alone — `42` became a Lua number, `true` a boolean,

   look at the column, then answered "Cannot assign number to varchar column", so the
   cell could not be edited at all. The DML layer had the right rule since round 12
   (a digit string in a text column is the characters, not a number); the editor was
   the one layer that had not been told. `infers_non_text` now gates the inference on
   the column's type: text spellings take the input verbatim, numeric and JSON columns
   keep the inference, and a column with no type at all keeps the older permissive
   behavior. 11 tests in `sql_editor_spec` (139 → 150) plus one in

10. **An integer cell accepted `Infinity`, and the rest of the integer family

    ctype against the single string `"integer"`, so `bigint` (what `int8` normalizes

    `tostring(math.huge)` is `"inf"` and carries no decimal point: typing `Infinity`

    measured — was accepted here and committed as `SET seq = 'Infinity'`. The family
    is now tested with this file's own `is_type` table, non-finites are rejected for
    it, and the floating families keep accepting them (an infinite `float8` cell is a
    supported round trip, and the editor side of that contract is pinned now). 4

11. **`validate_value` consulted a table that does not contain the names servers
    send** (`editor/cell.lua`, `types.lua`, `76e95f8`). Its numeric test was

    actually arrive carry parameters or widths from ClickHouse — `UInt64`, `Float64`,
    `Decimal(10, 2)` — all of which answered "not numeric". A number was therefore an
    invalid value for the very columns that hold numbers, and such a column could not
    be edited at all. Both checks now come from `poste-db.types`, the module the DML
    layer and the alignment check already asked, plus a new root-word `is_integer`
    sibling: without it a `UInt64` cell is numeric enough to parse and not-integer
    enough to skip the guards item 10 just added. An empty ctype is answered before
    any of this — `types.is_numeric` reads an unknown name as numeric because that is
    what picking a literal's shape needs, and taken as a validation rule the same
    answer would make a plain word an invalid value for a column nobody ever typed (a
    regression this round introduced, and its test caught in the same pass). 6 tests,
    2 red beforehand.
    One correction for the record: that commit message attributes the parameterized
    spellings to postgres' `format_type` and to MySQL. Round 28 read the senders and

12. **A ClickHouse `Nullable(Int32)` column rejected every number** (`types.lua`,

    layers answer the integer question identically; `is_integer_name` lost its last
    caller and went. 16 tests across 5 files, 7 red beforehand, plus a mutation proof

17. **A partially applied edit commit was journaled as a success**
    (`edit_commit/init.lua`, `log_viewer.lua`, `sql_log.lua`, round 34, `562aeac`).
    `commit_outcome` already distinguished the case — every statement ran, but fewer

    deleted by someone else — and the user got a `WARN` saying

    `status = "success"` and the reason thrown away. That is the second half of the

      naming who writes each value. Before this round an entry's `status` had exactly

      progress dialogs also match on `status`, but that is a per-statement result
      field of a different shape, not the journal's.

19. **An import chunk could be booked as a success while the server rejected all of
    it** (`import/execute.lua`, round 35, `37f6c86`). The chunk loop collected
    per-statement errors inside `if resp.has_error and body.results then`, so when the

    import then wrote `status = "success"`, added nothing to `all_errors`, and the run

    changed:

## Test-infrastructure findings

- **The spec process inherits the developer's Neovim config, and that changes
  measurements** (round 20). plenary starts each spec file in a *child* nvim
  without `-u` — the fact `tests/minimal_init.lua` already notes for
  `$POSTE_BINARY` — so `~/.config/nvim/init.lua` runs there. On this machine it
  sets `number` and `breakindent`, which is what turns the 77-column bar into 79
  cells: `number` narrows the wrap width under the line, and `breakindent` counts
  the leading blanks a second time for the continuation row. Any assertion about a
  line that nearly fills its float is therefore machine-dependent while it uses
  `strdisplaywidth`. `:verbose set breakindent?` in the spec child is the quick
  way to see this.
- **I tried to fix the leak and backed it out** (round 20). Redirecting
  `XDG_CONFIG_HOME` in both runners makes the spec child hermetic — measured:
  `number=false breakindent=false tabstop=8`, and the bar measures 77 — but it also
  removes the Tree-sitter `sql` parser that the same config installs. The gate went
  from 1595 to 1468 successes and 3 failures, all four deltas in
  parser-dependent specs: `sql_ts_stmt_spec` 108 → 1, `sql_multi_stmt_spec` 38 → 34,
  `sql_semantic_diagnostics_spec` 20 → 7, `sql_statement_indicator_spec` 8 → 5.
  124 of those tests *vanished from the tally* rather than failing: the specs guard
  a whole `describe` on `ts_stmt.check_parser()` and fall back to a single
  `pending` test. That is the same skip-by-absence shape round 18 removed from the
  binary guard, ~124 tests wide, and it is why the runner change is not in this
  commit. A hermetic gate needs the parser installed by the harness, not a config
  borrowed from the developer.
- **One parser-dependent spec had the worst of both patterns** (round 20, fixed).
  `sql_statement_indicator_spec`'s boundary `describe` had no guard at all: in a
  parser-less environment three tests fail on extmarks that can never appear, and
  the fourth — `does not paint single-line statements`, asserting *zero* extmarks —
  passes vacuously for the same reason. It now wraps all four in
  `it_needs_parser`, using the plugin's own `check_parser()` predicate, verified
  both ways: with the parser 8 passed / 0 failed with no SKIP printed, and with
  `XDG_CONFIG_HOME` redirected 8 passed / 0 failed with four explicit
  `SKIP: … no Tree-sitter sql parser` lines. Before the change that second run was
  5 passed / 3 failed.
- **Stubbing `poste-db.dataset` without stubbing its logic** (round 26,
  `sql_buffer_search_view_spec`). `filter_by_current_cell` reaches the buffer through
  that module, so the spec replaces it — but the function under test also calls
  `D.compute_view_indices`, and hand-writing that in the stub would have let the spec
  pass while the real view math broke. The stub therefore imports the real module
  first and copies that one field through (`compute_view_indices =
  real_D.compute_view_indices`), stubbing only the buffer/window collaborators
  (`buffer.render_dataset`, `buffer.nav.position_cursor`, `highlights`,
  `buffer.header`, `buffer.page`) and leaving `format` real so the layout is the one
  the app renders. Worth repeating: a stub is only safe for the parts whose
  behaviour the test does not depend on.

- **A spec can pin a function while leaving its call site untested** (round 27). The
  first mutation of the parse-value fix dropped the `col_meta` argument at
  `nav.lua`'s call — the exact way to unhook the new column-directed inference from
  the editor — and **0** tests went red. Not a failed proof: a finding. The 11 new
  unit tests all call `parse_value` directly, so nothing in the suite reached the
  line the UI actually runs. `sql_editor_row_mapping_spec` gained a test that drives
  `nav.edit_cell` end to end (stub `vim.ui.input`, answer `"42"`, assert the cell
  still reads `42` as text and that the committed statement is
  `UPDATE "users" SET "name" = '42' …`); the same mutation then turned exactly that
  one test red. A unit suite is evidence about a function, not about the app.
- **A spec can also pin a limitation and keep it alive** (round 28). `sql_types_spec`
  had `pins the other direction: a wrapped type reads as not numeric`, asserting
  `is_numeric("nullable(int32)") == false` and noting that widening the lookup
  should come with a spec here. When round 28 widened it, the honest move was to
  rewrite that test as the *contract* — unwrap first, then classify, so
  `is_numeric("nullable(int32)")` is still false and
  `is_numeric(unwrap_modifier("nullable(int32)"))` is true — rather than delete it.
  Left as it was it would have blocked the fix; deleted, it would have lost the
  reason the two-step exists.
- **The three cell editors had never run under a test** (round 29,
  `sql_editor_ui_spec`). Round 27's lesson was "a spec can pin a function while
  leaving its call site untested"; round 29 found the same shape one level up, over
  an entire feature: the editors were covered only through `parse_value` and
  `validate_value` called directly, so no spec had ever entered `cell_editors.boolean`,
  `.datetime` or `.enum`. That is why a branch could hand a prompt's raw text to the
  commit path for as long as it had existed. Stubbing is cheap here —
  `vim.ui.select` and `vim.ui.input` are plain assignable fields in this Neovim
  (0.12-dev, probed: no metatable), so the spec records the `opts.default` the editor
  prefills and calls the callback itself with the pick or the typed text.
- **… and a UI spec can be vacuous in a new way** (round 29, my own trap). The first
  version of that file measured 1 Success / 8 Failed: `edit()` installed the stubs
  and answered the callback, but never called `nav.edit_cell()`, so nothing reached
  the code under test and the failures were the asserts noticing an untouched cell.
  A stub-driven spec fails loudly only when the assertion looks at state; an
  assertion about a *callback argument* would have passed vacuously. Two things to
  keep in this shape: call the entry point in the helper that installs stubs, and let
  at least one assertion look at what the app stored. The useful red run is the
  second one — 6 of 9 failing against unmodified `nav.lua`, the five datetime/enum
  behaviours plus the already-NULL cell, and the three greens are the picks that
  worked before (the picker's own candidates, an enum value, a boolean), which is
  the shape a regression guard should have too.
- **A targeted run was not the gate's environment** (round 33, `eaabee1`). The gate
  (`tests/run.sh` → `:PlenaryBustedDirectory`) forwards `tests/minimal_init.lua`;
  `:PlenaryBustedFile` takes one argument and cannot forward options, so plenary
  started the spec child with `--noplugin` and *no* `-u`, and the developer's own
  `init.lua` was what ran there. One commit measured green under the gate and red in a
  targeted run of the same file, because a user `ColorScheme` autocmd counts
  `nvim_set_hl` calls and a spec stubs that function. `tests/run_one.sh` now drives
  `plenary.busted.run` with `-u tests/minimal_init.lua --noplugin`, and the flag is
  what makes the two environments equal rather than a speedup: `minimal_init.lua`
  appends `.` to `rtp`, so without it Neovim also sources this repo's own
  `plugin/poste-db.lua`, which preloads the real modules, and a spec that swaps
  `package.loaded` at file scope then binds a module that already holds the original —
  `sql_connections_spec` measures 28 passed / 38 failed that way and 66 / 0 with the
  flag. The `setup()` call that used to sit in that script only ever ran in the parent
  process, where no spec executes.
- **plenary's busted rejects file-root hooks** (round 34,
  `sql_edit_commit_journal_spec`). `before_each` / `after_each` called outside any
  `describe` crash the whole file with
  `busted.lua:143: bad argument #1 to 'insert' (table expected, got nil)` — no line
  number, and nothing in the message points at the hooks. Worth recognising on sight:
  it reads like a harness bug and is a file-shape bug.
- **A stub does not reach a module that already loaded its dependencies** (round 34,
  same file). `edit_commit` binds `dml`, `buffer` and `editor` as module-level locals
  at require time, so installing stubs is half the work — the subject has to be
  evicted too (`package.loaded["poste-db.edit_commit"] = nil`) before the test
  requires it. Without that line the spec drives the real DML generator against a fake
  response and still reports success.
- **A `run_async` stub that answers every dispatch re-enters its own callback**
  (round 34). The commit path refreshes the dataset after writing the journal, so the
  stub fires only when `#captured.dispatches == 1`; answering both makes the refresh
  callback run inside the commit callback, and the entries the spec reads afterwards
  are no longer in the order it claims.

## Recorded, not changed (with rationale)

- **An `if` whose then-branch is empty, with a lint waiver on it** (`buffer/init.lua:615`,
  round 26). `if tab.is_sorting then -- luacheck: ignore 542 else tab.sort = nil … end`
  encodes "only reset the sort when this render is not the sort's own re-render", and
  reads as a mistake every time someone opens the file — the inverted form
  (`if not tab.is_sorting then`) is the same behaviour without the empty branch. Left
  alone because touching `render_dataset`'s state resets is how rounds 21–23 found
  bugs elsewhere, and this one is cosmetic; it is the kind of change to make with a
  failing test that pins `tab.sort` surviving a sort re-render, not on the way past
  something else.
- **What round 22 deliberately left on the table** (`statement.lua`). Three
  residuals in the text fallback, each one cheaper to record than to design around:
  a **bare** mixed-case name still folds to lower case (`UPDATE Users` → `users`),
  because `read_identifier` has no dialect argument. A dialect *is* reachable at
  both call sites (`parsed.dialect` in `response.lua`, `tab.layout.dialect` in
  `edit_commit`), so the plumbing is small — what is not settled is the rule to
  plumb in: postgres and MariaDB fold unquoted identifiers, MySQL depends on
  `lower_case_table_names`, ClickHouse and MSSQL on collation, so a dialect-keyed
  fold would be a guess for three of the engines this plugin drives. The case
  where the intent is unambiguous — a *quoted* name — is the one this round fixed,
  and a name typed bare is the one the server itself may resolve loosely;
  the **qualifier** of
  `schema.tbl` typed in text is dropped, which is right for the dataset layout
  (it stores the schema separately) but means a buffer query that relies on an
  explicit schema different from the connection's default cannot express it here;
  and a **CTE** name comes back as the table (`WITH t AS (…) SELECT * FROM t` →
  `t`), since resolving it needs statement structure this helper does not have.
  All three are pinned by tests (`keeps the case of a quoted name, and folds an
  unquoted one`, `keeps only the last part of a three-part reference`,
  `still hands back a CTE name (recorded limitation)`) so the behaviour is written
  down in the suite, not just here.
  Correcting round 21's note on this line: it claimed the lowercasing "is also
  consumed by completion and semantic diagnostics". It is not — a call-site grep
  (`statement.extract_table_name`) finds only `sql_runner/response.lua`,
  `edit_commit/init.lua` and the two test stubs, and completion has its own
  parser path. That claim was inherited from an assumption instead of a grep, which
  is the reason the fix looked bigger than it was for a round.
- **The generators still take any name they are given** (`dml.lua:135,168,188`).

- **What the ClickHouse names still cost the editor's UI** (round 28, probed rather
  than inferred, through `plan_resultset_layout` so the ctypes are the ones the
  editor sees). `Nullable(Int8)` normalizes to `bigint` — the map is postgres-flavored

  cells get the plain text input rather than the date picker; `Array(Int32)` answers

  to `poste-db.types`. Fixing the date and array cases means deciding whether an
  *element type* should ever reach those checks, which is a design question, not a
  missing lookup — and each deserves its own failing test, not a ride-along.
- **The display helpers still print the bare Lua spellings** (`format.lua`
  `format_number`, `nav_cell.pretty_print` / `clipboard_text`, round 25). Probed
  directly: each renders a non-finite *number* as `inf` / `-inf` / `nan`, not as the
  `Infinity` / `NaN` the engines print. Reachable one way: `editor/nav.lua:93` puts
  an edit's parsed value into `tab.layout.rows`, so typing `Infinity` into a cell
  previews it as `inf` while the committed row will read `Infinity`. Not changed:
  the correct preview is dialect-dependent — ClickHouse's rows really do carry bare
  `inf` — and `cell_to_string` has no dialect to ask. Passing one down for this
  alone is a wider change than the mismatch is worth; a number in the *wire* path
  is impossible since `08acb28`, so only a typed edit can reach it — and since round
  27's item 10 an integer column refuses that edit outright, so what is left is the
  floating columns, whose committed row really does read `Infinity` while the
  preview says `inf`.
- **The value converters are still two families** (`poste.nvim`
  `sql_values.rs` vs `sql_executor/*/value.rs`, round 24). Only the float rule is
  shared now; the rest of the per-dialect decoding remains duplicated between the
  plugin's executor and the CLI's session/exec-file paths, with a header comment
  asking the two to stay in sync. Unifying them is a real refactor and the drift
  that actually caused a bug was this one rule, so the layout stayed.
- **Round 30 fixed the delete path in the UI layer, not the generator** (`nav.lua`,
  `dml.lua`, round 30). `generate_delete` still takes `rows_source[row_idx]` exactly
  as it stands, and `editor.lua` still re-exports `track_row_delete`, so a caller
  that queues a delete without `delete_row`'s revert builds the WHERE from the
  pending values — measured through the tracker directly:
  `DELETE FROM "codes" WHERE "code" = 7 AND "ts" = '__expr:CURRENT_TIMESTAMP';`.
  No code path in the plugin does that today (only specs that call the tracker), and
  each alternative is worse than the line it would replace: moving the revert into
  `track_row_delete` makes the tracker read a tab it does not own, and overlaying

  discard is the design being questioned, not the missing lookup. If a second caller
  appears, the fix is to stop discarding `modified_cells` for a deleted row and let
  `generate_dml` rebuild the row for DELETE the way it already does for UPDATE, so
  "the row as the server has it" has one representation instead of two.
- **A cell cannot hold text that begins with `__expr:`** (`cell.lua` `parse_value`,
  `format.lua:153-154`, found while documenting round 31). The prefix is the editor's
  expression hatch, so typing `__expr:hello()` into a *varchar* cell stores it as raw
  SQL — measured: `UPDATE "t" SET "label" = hello() WHERE "label" = 'old';` — and the
  renderer strips the prefix for display, so the cell shows `hello()`. Not changed:
  the hatch is intended (and imports pass no `allow_expr`, so a crafted CSV cell
  cannot reach it — round 12), the alternative is a second escape spelling for a
  three-in-a-million input, and the user-visible half is now stated on the docs page
  rather than left to discover.
- **A link-local IPv6 address with a zone id is still not bracketed** (round 32).
  `fe80::1%eth0` fails the "hex digits and colons only" predicate on both mirrors, so
  it reaches the URL exactly as written, and the host is not percent-encoded either
  (the 09-20 note). Not changed because widening the rule to accept `%` would make
  "is this an address or a host with a stray percent" undecidable, and because the
  already-bracketed form passes through untouched — the workaround is to write the
  host the way the URL wants it. What the drivers then do with a percent inside the
  authority was not measured, so this file does not claim a zone id works after
  bracketing, only that the plugin stops rewriting it.
- **`first_error` reports one error per response** (round 34). A batch where two
  statements fail with different messages surfaces the first. Left as is because both
  call sites notify a single line, and the batch dialog already keys its per-table
  errors by label, so the only loss is a second message about the *same* table. The
  moment a caller wants all of them it should return a list rather than a second
  helper.
- **The commit path truncates its own error text before the writer does**
  (`edit_commit/init.lua:288,323`, round 34). `detail:sub(1, 500)` repeats the limit
  `sql_log.record` already applies through `MAX_ERROR_LEN`, so the constant now lives
  in three places. Not changed mid-round: the rolled-back branch has carried that
  `sub` since before this pass, and halving it would leave the two branches of one
  function reading differently. The clean version is to delete both call-site
  truncations and let the writer own the policy — which wants the limit exported or
  the callers trusting a documented invariant, so it is its own commit with its own
  test that a long reason survives a write and gets cut at the writer's length.
- **"Expected rows" now has two definitions** (`edit_commit/exec.lua:61` and
  `log_viewer.lua`'s `edit_summary_line`, round 34). The viewer sums
  `updates + inserts + deletes` inline because requiring `edit_commit.exec` from a
  display module drags in the commit pipeline. Both read the same
  `edit_summary` fields, so the duplication is a shape agreement rather than a
  behaviour fork — but a second writer of `edit_summary` that used different keys
  would make the viewer print `0 of 0`, which is why the note is here and not a
  comment.
- **`M._pad_table(s, width)` writes module state** (`log_viewer.lua:754`, pre-existing,
  noticed while adding the mark column). Passing a width sets `TBL_W` for every later
  `summary_parts` call in the process, so a spec that pins the padding leaks that width
  into unrelated specs' rows in the same file. This round's assertions therefore match
  the db segment with `find` rather than equality; the fix is a parameter on the hook
  instead of a write, which the next round that touches the layout should do together
  with the tests that currently rely on the leak.
- **Round 35's fallback sentences are not one shared constant** (`sql_log.lua`,
  `ai/actions.lua`, `import/execute.lua`, `db_browser/copy.lua`,
  `db_browser/sql_conn.lua`). Unifying them would mean a module all five can require,
  and `sql_log` cannot require `exec_run` without a cycle; each sentence also addresses
  a different reader — the chat transcript, a red row in `<leader>l`, the import error
  dialog, the clone wizard's notify — so the wording that fits one is too terse or too
  wordy for another. Three short strings inside their own modules is the cheaper
  agreement. What *is* shared is the rule, now written down in
  `poste-db-dev/execution-pipeline.mdx` ("标志位是结论，错误文本只是解释") so the next
  envelope reader is pointed at it.
- **`copy.check_response` still reads the first statement's text only** (round 35).
  `check_result_error(decoded)` looks at `results[1]`, and the flag guard is the last
  resort rather than a smarter reader: if a batch's *second* statement failed *with* a
  message, the verdict is now correct but the reason shown is
  `the response reported a failure whose statement carried no message`, which is true
  of the first statement and misleading about the batch. Not fixed in this round
  because the clone wizard's writes are single-statement today, so the shape needs
  `exec_run.first_error` (which already walks all results) — the clean change is to
  make `check_result_error` use it and drop the "first" from its name, which touches
  every message the wizard can produce and wants its own pass.
- **A failed import chunk does not record how many rows landed** (round 35). The
  chunk's journal entry has `status = "error"` plus `N statement(s) in this chunk
  failed: …`, and under greedy mode the non-failing statements are committed, so the
  row states a failure whose size is unknown. `affected` is computed right there and
  only thrown away on the error branch. Not folded into this round: `partial` is the
  vocabulary edit commits use, and importing the word would make `<leader>l`'s `!`
  mark mean "rows" in one source and "statements" in another. The minimal version is
  to add `affected_rows` to the error branch's entry so the number is at least in the
  JSON.
- **Test debt from round 35**: `actions.lua show_table_info`'s stderr-to-journal change
  has no direct test. Reaching that line needs a browser buffer whose line numbers map
  to a table node, i.e. the whole `line_to_node` scaffold, and the same idiom is
  covered end-to-end by the two new `show_ddl` tests in
  `sql_db_browser_operations_spec.lua`. What is untested is that the second copy kept
  the behaviour, not whether the pattern works.
