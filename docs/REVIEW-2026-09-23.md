## Bugs fixed

30. **A refused metadata lookup was cached as "no keys"** (`editor/column.lua`,
    `a1b1784`). `ensure_primary_key`'s cache rule is "only on success" — the
    comment said so — but the success it meant was the transport's: a statement
    the server refused arrives from `exec_run.run_sql` as a *delivered*
    response whose body carries one failed result with no rows, textually the
    same payload a keyless table produces. `run_introspection_query` decoded
    it, the parsers found nothing, and `pk_cache[cache_key] = true` stored the
    verdict for the session — a revoked grant or a transient error cost the
    editor its key/enum/default metadata on that table until restart, with the
    only trace being DML that quietly built keyless WHERE clauses.
    `run_introspection_query` now consults `parsed.has_error` /
    `exec_run.first_error` and returns nil for a refused query, which is what
    the cache rule already promised; the user gets the server's reason as a
    WARN. The enum query runs through the same helper and is covered by the
    same guard. Pinned by 4 tests in `sql_editor_column_spec` (3 → 7): the
    refused lookup retries on the next edit, leaves the key verdict unset,
    a success after a refusal is parsed *and then* cached, and a genuine
    no-keys answer still caches (that one pins the flip side the fix must not
    disturb). Both retry tests are red at HEAD; the other two pass at HEAD on
    purpose.
    One test-infra trap the spec now documents in place: the module caches the
    first `require("poste-db.state")` it sees for its whole lifetime, and this
    file's earlier describe block pins it to a connection-less stub — so the
    new tests carry the connection on the layout (`_conn_name`) instead of
    stubbing state, which would silently keep the poisoned copy.

31. **Column yank ignored the view, one commit after cell yank learned not
    to** (`buffer/nav_cell.lua`, `a9a34e7`). The merge `7da9560` fixed
    `get_resultset_cell` — "the data lives in the full result set, so
    page/sort/filter offsets must be undone first" — and `yank_column` sat one
    function away reading `ipairs(res.rows)` directly. After a sort, `yc`
    pasted the column in source order so it no longer lined up with the rows
    on screen; after a filter, it pasted rows the user had filtered away.
    `collect_column_values` now iterates `tab.view_indices` when the tab has
    one (view order, filtered rows only) and falls back to the whole column in
    source order otherwise — the default behaviour is unchanged, and the
    `view_indices → layout.rows → res.rows` identity (plan_resultset_layout
    hands the table through) means no second mapping is needed. 1 test added
    to `sql_buffer_nav_cell_spec` (10 → 11), red at HEAD; the pre-existing
    no-view test pins the unchanged default.

32. **A JSONB cell exported as a table address** (`export.lua`, `62b35ca`).
    The csv/tsv/md formatters and `sql_escape_val` called `tostring` on every
    cell, and a jsonb cell reaches Lua as a *decoded table* — so an exported
    field was the pointer spelling `table: 0x…` while the dataset on screen
    (compact-encoded by `cell_to_string`) and the yanked cell
    (`nav_cell.clipboard_text`) both show the JSON the column holds. Every
    text format now follows the same rule the renderer and the yank path
    already implement; the SQL INSERT format writes one JSON string literal,
    which round-trips on all dialects this plugin drives. 2 tests in
    `sql_export_spec` (34 → 36), both red at HEAD.

33. **A failed write or rename reported success** (`export.lua`, `31b2dbc`).
    `export_to_file` opened the `.tmp`, wrote unchecked, renamed unchecked and
    then notified `Exported N rows (path in clipboard)` — so a full disk or an
    unplaceable path ended in a success claim with the data stranded in a
    stale `.tmp` beside the target. Both halves are checked now; the
    half-written temp file is removed on either failure and the error names
    the stage. No test: reaching the failure branch needs an `io.open` that
    succeeds and a *write* that fails (a full disk), which is not reachable
    from a sandboxed spec without stubbing globals the file reads directly.

34. **A quoted CRLF did not survive a CSV round trip**
    (`import/format.lua`, `5f3c358`). `parse_csv` blanket-rewrote every CRLF
    to LF before scanning, including the ones *inside* quoted fields — which
    are the cell's data per RFC 4180. `csv_escape` on the export side quotes
    an embedded CRLF precisely so it survives; the import half then changed
    the value back to a bare LF, so export → import was not the identity the
    quoting exists to provide. Line-ending decisions moved into the scanner,
    which can see whether it is inside quotes; a CRLF outside quotes still
    ends the row, and the pre-existing pin for that (`normalizes \r\n line
    endings`) passes unchanged. 1 test in `sql_import_spec` (32 → 33), red at
    HEAD.

## Recorded, not changed (with rationale)

- **Export always writes `results[1]`** (`export.lua get_current_data`). A
  multi-statement run exports its first result set and says so nowhere. Every
  picker in the flow would need the count of result sets to make the choice
  real, so this is a feature decision (an "which result set?" picker), not a
  one-line warn.
- **`parse_csv` is lenient after a closing quote** (`import/format.lua`):
  `"a"x,b` reads as `ax`. RFC 4180 leaves the shape undefined; both redis and
  the strict parsers disagree among themselves, and the value at least stays
  in its own field. Recorded so the leniency is a decision, not an accident.
- **`buffer/history.lua`'s time-column highlight addresses bytes with a
  cell-computed start** (see Verified). Fixing it means computing the byte
  offset of the time region from the rendered line, which the builder knows
  and refresh() re-derives — worth doing when that sidebar next changes, not
  as a ride-along.
- **`dml_guard` does not classify MERGE** (`missing_where`). A `MERGE` without
  `ON` can hit every row, but tree-sitter-sql's merge shape varies by grammar
  version and the plugin has no MERGE-specific UI; adding a half-understood
  node type to a safety gate is worse than documenting the gap.
- **`generate_filename` sanitizes path separators but keeps other odd
  characters** (`export.lua`). A table named `..` or `-rf` cannot produce a
  path traversal through this function (no separator survives), and cosmetic
  escaping of dots/dashes in filenames would rename exports users may already
  script against.

## Queued from the LIMIT offset,count session (same day, handle next round)

A bug-fix session between rounds (`ea06360`, `fix(treesitter)`) stopped
`LIMIT 1, 10` reporting a treesitter error: the grammar strands `, 10` as a
top-level ERROR sibling after `limit 1`, now dialect-gated out of
`find_error_nodes` (mysql/mariadb/sqlite/clickhouse), folded into the
preceding statement's span in `build_span_list`, skipped as a statement start
in `get_top_level_stmts`, recolored in `syntax.lua`; 12 tests, gate
**1794 / 0 / 0** over 110 files, luacheck 0 / 0 / 251. Two findings from that
session are queued here for next time:

- **The plugin's own `### dialect` header reports as
  `Unexpected token: ### dialect mysql`** — the header `diagnostics.get_dialect`
  and `source_format.lua` treat as input (`^### dialect%s+(%S+)`) parses as a
  top-level ERROR, and no filter rule covers the plugin's `###` directive/section
  lines (headless probe on `ea06360`^, line 1 of a `poste_sql` buffer). Being a
  top-level sibling it has the same second face the LIMIT fragment had: it
  registers as a statement in `find_stmt_span`/`get_top_level_stmts` (some
  extraction paths skip `###` lines by text, not by tree). Fix along the same
  three-consumer alignment as `is_limit_comma_fragment` — filter (probably
  dialect-free, the header is the plugin's own format), fold/skip in the two
  span builders, recolor in `syntax.lua` — with the paired red/green tests and
  a probe of the recovery shapes (`###` line followed by SQL with/without a
  blank line).
- **A LIMIT comma fragment without `;` swallows the next statement and stays
  reported** (`ts_stmt.lua is_limit_comma_fragment`). `LIMIT 1, 10` with no
  semicolon before `SELECT 2;` parses the ERROR as `, 10\nSELECT 2`, the
  anchored match declines it, and even a mysql buffer keeps the diagnostic.
  Accepted this session as the conservative direction — un-anchoring would hide
  real errors, and loosening to a recovery-shape rule (`, <digits>` head plus
  re-scanned tail) means trusting a boundary tree-sitter chose by luck. Revisit
  only if the no-semicolon mid-buffer form shows up in real files.
