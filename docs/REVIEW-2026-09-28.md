## Fixes (each with tests)

- **`run_sql` unlinked the exec-file input between spawn and wait.**
  `exec_run.lua` wrote the SQL to a temp file, called `vim.system`, deleted
  the temp file, *then* `wait()`ed. `vim.system` returns as soon as the child
  is spawned, so the delete raced the child's first `open()` — on a loaded
  box the run fails with "file not found" for a file the user never touched.
  Every synchronous path goes through here (EXPLAIN, Test Connection,
  `editor/column` metadata, `db_create` role probe). The delete now happens
  after `wait()` (and in the spawn-raised branch, where nothing was started).
  Pinned by a lifecycle spec: the file must still exist inside `wait()`, and
  a failed spawn must not leak it.

- **`async.run` delivered a failed start twice.** When the poste binary was
  missing, `cli.run_async` synthesized a synchronous `on_exit(-1)` and
  `async.run`'s failed-start branch *also* fired `on_error("Failed to start
  job")` for the same run. The only `async.run` caller — the browser's
  `run_introspect` — journals and notifies on each delivery, so one missing
  binary produced two journal rows and two error toasts. The synthesized exit
  (identifiable by arriving before any job existed) is now swallowed; the
  failed-start branch is the single delivery. First spec for `async.run` pins
  the whole contract: error/exit mutual exclusion, cancel, timeout.

- **The browser's top-level connection list reshuffled.**
  `db_browser/async.load_connections` built its nodes straight from `pairs()`
  over the parsed toml — the same churn fixed in the connection picker last
  round (`c1fba86`), in the sibling code path this time. Sort by name before
  building nodes.

- **The JSON cell editor seeded its prompt with invalid JSON.**
  `editor/cell.format_json_input` stripped the encoder's `\"` escapes, so any
  JSON/JSONB value carrying a quote displayed as `{"note":"he said "hi""}` —
  and even a no-op edit of that cell failed to re-parse. Plain encode, escapes
  intact; round-trip pinned.

- **JSON export silently dropped duplicate result columns.**
  `SELECT a.id, b.id FROM a JOIN b` exported as `[{"id":2}]` — one JSON key
  slot per object, last write won, the first column's values gone, while the
  CSV/TSV/Markdown/SQL exporters kept both. Duplicates are now disambiguated
  with a numeric suffix (`id`, `id_2`).

## Audited, no bug (recorded because it looked like one)

- **`session_conn.cleanup_buf` → `M.stop(pool_key)` looks like it kills
  sibling-database sessions** (stop's bare-URL branch matches every pool key
  carrying the same `conn_url`). It does not: the pool key embeds the
  database (`url\0db`), which can never equal a bare `conn_url`, so the match
  is exact. A fix was written and committed for this, then reverted after the
  reverse-verification run stayed green — the "bug" was an analysis error,
  not a code one. The reverse-verification step is what caught it; grep-and-
  reason alone had confidently shipped a false fix message.

## Observed, left alone (each verified, none actioned)

- **`format_json`'s suffix can still collide**: a resultset that already has
  an explicit `id_2` column beside two `id` columns synthesizes `id_2` a
  second time. The same trade most exporters make; a full uniquifier needs a
  policy decision about which column owns the clean name.
- **`guess_table` prefers the first `FROM`**, so `UPDATE t SET x = (SELECT …
  FROM other)` tags the journal row `other`. Display heuristic only; the
  journal's own `table` field wins before the guess is consulted.
